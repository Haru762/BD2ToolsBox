### 3.6 实现期发现并修复的真缺陷（**自查，不是复核抓到**）

`snapshotStore` 起初写成 `private val snapshotStore: ModSnapshotStore? get() = appContext?.let { … }`
—— **每次访问都新建��例**。`capture` 分配的 `revision` 是**实例状态**，于是 `capture` 与
`commit` 落在两个不同实例上，后者计数器还是 0 → **每一次提交都被判成 `Skipped`，快照永远写不出去**。
debug 下没有任何异常，只有一条 `Log.i`。

**修法**：改成按 `filesDir` 缓存的单实例（`snapshotStoreDir` / `snapshotStoreInstance`）。

**首版声称「JVM 侧补了两条对照用例钉住这条不变式」—— 二轮复核证明这句话不成立**：
那两条（`pendingWriteIsOnlyHonouredByItsOriginatingInstance` +
`pendingWriteFromTheSameInstanceIsHonoured`）守的是 **`ModSnapshotStore` 自己的 API 语义**
（revision 是实例状态），**与 `MainViewModel.snapshotStore()` 是否缓存毫无关系**。
把 `snapshotStore()` 改回每次新建之后**全量 JVM 套件 221 条全绿**（复核者攻击 D）。
JVM 上构造不了 `MainViewModel`（无 Robolectric），所以这条不变式**在首版交付态里没有任何
自动化用例守卫**。

**二轮的修法**：新增**设备侧**守卫 `SnapshotStoreInstanceReuseTest`
（`theSnapshotCallSitesShareOneStoreInstanceSoCommitActuallyLands`），
驱动生产入口 `deleteAbnormalMods`（公开方法）的收尾 `finally` —— 它**无条件**做
`capture` → `commit`，断言的对象是**磁盘上的快照文件**。它**不使用反射去够被测方法**
（只在依赖注入处反射写 `appContext` 一个字段，与 `TryUseBackupTrustGateTest`/`LedgerRecoveryStartupTest`
的既有范本同款），**不经过 `initialize()`**（那会拉起 Chaquopy 的 `checkLocalBundles`；
首版守卫走了 `initialize()`，注入攻击时崩在 `UnsatisfiedLinkError` 而不是断言上，
已改掉）。对照证伪见 §11.1（真缺陷 3）：改回每次新建 → 该用例**在断言处红**。

**这条不变式是「调用方必须复用实例」，Store 侧不该用全局状态去掩盖调用方错误。**

## 6. release 契约的证据（裁定 D）

### 6.1 为什么 DTO 必须有 keep 规则 —— 引用 §2.2 的实测

0.2.16 release 的 `MainViewModel$ModListSnapshot`：字段被改名为 `a`/`b`/`c`，
`version` **整个字段消失**，版本闸被 R8 折叠 → **生产包里根本没有版本闸**。
T10 的 `SnapshotV1` 就是这份 DTO 的后继，若不保护，R8 会做**完全相同的事**。

### 6.2 本机实测：去掉 keep → R8 复现 0.2.16；加上 keep → 字段保留

**能跑 R8 就跑**（裁定 D 问「能跑 R8 就实测」）：本机 `./gradlew :app:minifyReleaseWithR8`
**可跑**（BUILD SUCCESSFUL）。做了**三组对照**：

| 实验 | keep 配置 | `SnapshotV1` 在 release mapping 里的字段 |
|---|---|---|
| **A** | 去掉 `core.storage` 的**全部** keep | `int version -> a` / `long savedAt -> b` / `java.util.List mods -> c` / `java.util.List sourceDirs -> d`；`getVersion():251 -> d` —— **与 0.2.16 同一现象** |
| **B** | 只留包级规则 `-keep class com.bd2toolsbox.core.storage.** { *; }`（T08 加的），去掉 T10 的两条 | `getVersion` / `getSavedAt` / `getMods` / `getSourceDirs` **未被改名** |
| **C** | **交付态**（包级规则 + T10 两条 + `-keepattributes RuntimeVisibleAnnotations`） | 同上，成员名全部保留；类名也保留（`…ModSnapshotStore$SnapshotV1 -> …ModSnapshotStore$SnapshotV1`） |

→ **实测确认了一条与我的首版注释相反的事实**：包级规则 `core.storage.**` **确实覆盖嵌套类**
（`…ModSnapshotStore$SnapshotV1` 也吃到）。所以 T10 新增的两条 `-keepclassmembers` 是**纵深**，
**不是**「今天不写就会坏」的那类。`proguard-rules.pro` 的注释已按这一实测改正
（首版曾写「包级规则不匹配嵌套类」，**是错的**，已改）。

**留着的理由**（写进规则注释）：**磁盘格式的守卫不该只依赖一条包级规则**。T13/T14 会调 R8 配置，
「整包放开」正是最容易被换掉/收窄的一条；届时这两条显式规则替持久化格式兜底。这是 T09 二轮那条
教训的另一面 ——「持久化格式不许依赖会被改的东西」：今天是反射字段名，明天是包级 keep。

### 6.3 `version` 为什么不再被折叠（**决定性：DEX 探针**）

|---|---|---|

| `本次不落快照` | — | 1 |
| `按没有快照处理` | 1 | 1 |
| `写入冷启动快照失败` | 1 | 1 |
| `getVersion` / `getSavedAt` / `getMods` / `getSourceDirs` | — | 各 ≥1（方法名保留） |

**另**：交付态 release mapping 的 `ModSnapshotStore` 类块里，**版本闸源码行有字节码归属**
（首版是 `:447`；**二轮更正**：真缺陷 2 的注释更正把 `ModSnapshotStore.kt` 从 504 行推到

### 10.1 `version` 的类型宽容面（**二轮补登**，复核 §4-措辞#2）

`SnapshotV1.version` 是 `Int`，由 Gson 反序列化。**实测**（二轮自跑边界探针，
探针文件跑完即删；下表是 `ModSnapshotStore(snapshotFile).load(emptyList())` 的**真实分态**）：

| 磁盘上的 `version` | 实际分态 | 说明 |
|---|---|---|
| `1`（当前 `SCHEMA_VERSION`） | `Loaded` | 正常 |
| `0` / `-1` / `2` / `99` | `StaleVersion(n)` | 任一不等于 1 的**整数**都被闸挡住 |
| `null` | **`Loaded`** | ⚠️ Gson 跳过该键 → 走 Kotlin **无参构造器的默认值 `SCHEMA_VERSION`**（**不是**「折成 0」；实测直接反序列化 `{"version":null}` 得 `version=1`） |
| `"1"`（字符串） | **`Loaded`** | ⚠️ Gson 把字符串 `"1"` 折成 int `1` |
| `1.9` / `1.0`（小数） | **`Loaded`** | ⚠️ 被截断成 `1` |
| `"2.0"` / `"x"` | `Corrupt` | `NumberFormatException` |
| `true` / `{}` / `[1]` | `Corrupt` | Gson 抛 `IllegalStateException`（Expected NUMBER） |

**这是一条「语义选择」，不是缺陷**：`null` / `"1"` / `1.9` 折成 `1` 后**恰好等于
`SCHEMA_VERSION`**，语义上「就是 v1」，所以走 `Loaded` 是**容忍式解析**（tolerant parsing）；
`0` / `-1` / `2` / `99`（折完之后**不等于** 1）才落 `StaleVersion`。这与 §8.1 的
「损坏/未知版本显式失效」并不矛盾 —— 那条管的是**版本不认识**，这里三个输入折完**是认识的**。

**代价（必须写明）**：**将来若有人把磁盘键写成 `"version":"1"` 或 `1.9`，会被静默接受**
（当成 v1 读，不报错、不失效）。`malformedSnapshotsAreCorruptNotSilentlyEmpty` 的 7 种坏法
**没有一种覆盖 `version` 的类型错**。

**二轮的选择：保留宽容，只登记（不收紧）**。理由：收紧（在 `parse` 里对 `version` 先做
`isJsonPrimitive && isNumber` 检查、非数字一律 `Corrupt`）会**改变现有语义** ——
`null`/`"1"`/`1.9` 目前都落 `Loaded`，收紧后变成 `Corrupt`（进而 `discard()` 删快照），
**超出二轮定点整改的授权**（复核 §4-措辞#2 也把它列为「应改」而非 go 的条件）。
**留给编排者裁定**：若要收紧，是 T13/T14 或后续任务的语义变更，且应同步补一条
「`version` 类型错 → `Corrupt`」的用例。
