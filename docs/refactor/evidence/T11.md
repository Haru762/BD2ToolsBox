### 3.4 alias 命名方案（**T12/T14 沿用同一套**，主契约裁决点 E 要求单独成节）

**`[versions]` —— camelCase，按「它给什么定版本」命名，不按构件名。**

| 组 | 键 |
|---|---|
| 构建插件 | `agp` / `kotlin` / `chaquopy` |
| 构建参数（非依赖，但同样在两个模块各写一份） | `compileSdk` / `minSdk` / `targetSdk` / `javaVersion` |
| 依赖版本 | `composeBom` / `composeCompiler` / `coreKtx` / `lifecycle` / `activityCompose` / `documentfile` / `gson` / `junit` / `mockk` / `coroutinesTest` / `androidxTestCore` / `androidxTestRunner` / `androidxTestJunit` / `espresso` / `shimmer` / `shizuku` |

> **两处倒序命名要说明**：`shimmer` 的构件名是 `compose-shimmer`（坐标 `com.valentinilk.shimmer:compose-shimmer`），alias 按「库名优先」写成 `shimmer.compose`（与 `compose.ui` 那套「组名优先」相反）—— 前者是**库自己的构件命名**，后者是**AndroidX 的组命名**，两套都遵从上游事实，不强行统一。`shizuku` 同理（`dev.rikka.shizuku:api` / `:provider`）。

**`[plugins]` —— kebab-case，取插件 id 去掉厂商前缀后的可辨识部分。**

`android-application`（`com.android.application`）/ `kotlin-android`（`org.jetbrains.kotlin.android`）/ `chaquopy`（`com.chaquo.python`）。

**`[libraries]` —— kebab-case，规则是「组前缀尽量保留、构件名去掉与组重复的段」：**

| group:artifact | alias | 规则 |
|---|---|---|
| `androidx.core:core-ktx` | `androidx-core-ktx` | `androidx.<g>:<a>` → `androidx-<g>-<a>` |
| `androidx.lifecycle:lifecycle-runtime-ktx` | `androidx-lifecycle-runtime-ktx` | 同上（组名 `lifecycle` 在构件名里重复也保留，取完整可读） |
| `androidx.compose.material:material-icons-extended` | `androidx-compose-material-icons-extended` | `androidx.<g>.<s>:<a>` → `androidx-<g>-<s>-<a>` |
| `com.google.code.gson:gson` | `gson` | 第三方，取产品名 |
| `dev.rikka.shizuku:api` | `shizuku-api` | 第三方，厂商名 + 构件名 |
| `org.jetbrains.kotlin:kotlin-stdlib` | `kotlin-stdlib` | 第三方，去 `org.jetbrains.kotlin` 前缀 |

**三条纪律（写进 TOML 顶部注释，T12/T14 直接继承）：**

1. 只放「依赖与插件的版本」；App 发版号在 `gradle/version.properties`，**不在这里**。
2. 禁止动态版本：不得出现 `+`、`latest.release`、区间（`"1.0,)"`）或 `-SNAPSHOT`。
3. 由 BOM 管版本的构件**不写 version**（`androidx-compose-ui` 系列 8 条全部无 version）——
   用了 BOM 还写版本会让 BOM 失效。

**`composeCompiler` 刻意独立：** 当前 `1.5.1 ≠ Kotlin 1.9.0`，写成 `version.ref = "kotlin"`
会在 T11 当场改值（违反「只搬迁不升级」）。T14 才把它对齐 Kotlin 并换成
`org.jetbrains.kotlin.plugin.compose` 插件。

**Kotlin DSL 前缀歧义已被实际构建证伪：** `androidx-compose-ui` 与 `androidx-compose-ui-graphics`
是前缀关系，Kotlin DSL 生成 `libs.androidx.compose.ui` 与 `libs.androidx.compose.ui.graphics`；
两者在 `app/build.gradle.kts:180-181` 同时使用且**构建通过**（§4.1），说明 Gradle 的
accessor 生成对这对前缀没有歧义（前一轮的独立探针因路径空格失败，未提供证据，见 §8）。

### 3.5 `release-probe` 纳入 catalog（主契约裁决点 A）

计划「文件范围」漏列了 `release-probe/build.gradle.kts`。按主契约 §3.4 的建议选**一并迁进 TOML**：
否则 T14 升级 Kotlin 时探针的 `kotlin-stdlib:1.9.0` 会与 `:app` 的 Kotlin 2.x 静默分叉，
探针运行时可能与被测包不兼容。**TOML 中 `junit` / `kotlin-stdlib` 被两个模块共用**，

### 3.6 校验与覆盖（计划「验收」第 2 条的口径）

`app/build.gradle.kts:18-51` 在**配置阶段**（不是执行阶段）用 `GradleException` 抛错：

- `gradle/version.properties` 缺失 → 失败
- `appVersionName` 缺失 / 空 / 纯空白 → 失败（`APP_VERSION_NAME` 覆盖后**仍须**过同样的校验）
- `appVersionCode` 缺失 / 非十进制整数 / `<= 0` → 失败

**「发布时递增」是流程约定，本任务不实现自动判定**（单次构建无从得知上一次的值），
如实登记在 `gradle/version.properties:14-17` 与 §6.2。

### 5.2 dex 差异的精确描述（**登记项，不是判据**）

> **口径更正（本轮硬要求）**：不许写「dex 逐字节不变」。
> 二轮说「只有一条超长 hash blob 字符串不同」**字面为真但严重低估** —— 那是 **50 条哈希变了**。

**交付态与全回退态的真实差异（`classes.dex`）：**

| 项 | 值 |
|---|---|
| 字节数 | 44,544,060（全回退 `36b957ce…`）→ 44,544,064（交付态 `963ebf88…`），**+4 B** |
| 字符串总数 | 两边都是 **122,700** |
| 不同的字符串 | **恰好 1 条** —— 就是那条 `~~~{…}` 死元数据 blob |
| 那条 blob 里的条目数 | **17,891**（与 `classes.dex` 的类数精确相等，见下） |
| 其中哈希不同的条目 | **50 条**：49 条 `$$ExternalSyntheticLambda<N>` + 1 条 `MutatorMutex$$ExternalSyntheticBackportWithForwarding0` |
| blob 字符串长度 | 1,305,660（全回退） → 1,305,665（交付态），**+5**；整条 `string_data_item`（uleb 长度 + 内容 + NUL）1,305,664 → 1,305,669，也是 **+5** |
| dex 文件字节 | 44,544,060 → 44,544,064，**+4**。**注意**：blob 长了 5 字节而 dex 只长 4 字节 —— 差值被 `string_data` 之后的对齐填充吸收。**不要写成「+4 字节」去描述 blob 本身。** |
| **全部字节码** | **逐类比对 0 个类不同**（`dexdeep.py`：id 表除 strings 外全同，`class_data` 17784 个类全同） |
| 该 blob 的指令引用 | **0 次**（`refcheck2.py` 扫全部 `const-string` / `const-string/jumbo`） |

**这条 blob 是什么（本轮新增的实测事实，前两轮没有）：**

- 键**精确等于**该 dex 的 `class_defs` 类描述符全集：`classes.dex` 17891/17891、
  `classes4.dex` 452/452、`classes7.dex` 154/154、`classes8.dex` 156/156、
  `classes13.dex` 5747/5747，五个 dex **全部 EQUAL**，extra=0 / missing=0。
- 值形如 Java 有符号 32 位整数的紧凑十六进制（4–10 字符，可带负号）；
  **不是** `String.hashCode(key)`（17891/17891 不匹配）、**不是** crc32 / adler32 / sha1/md5 前缀。
- 它**每个 dex 各有一条**：`classes.dex`（17891 条）、`classes4/7/8.dex`（该 shard 的类）、
  `classes13.dex`（5747 条）。

→ **它是 D8 写进每个 dex 的簿记（key=类、value=类字节摘要），运行期不可达（零指令引用）。**

1. **`E-A` 是无效数据点（构建失败，哈希取自残留），必须从矩阵剔除。**
   核对 `local/refactor-artifacts/test-results/20260918-123000-t11r2-E-A/build.log` 实测是

   **这条同时暴露了一个方法论缺陷**：`Build-And-Hash.ps1` 只看磁盘上的 APK，
   **不校验 Gradle 退出码**。二轮矩阵里凡是 `BUILD FAILED` 的行都可能读到上一次的残留。

   在配置未留存的情况下**不足以单独支撑结论**。

2. **「无 catalog → `36b957ce…`」仍成立**（X4/X4b/X4c 三次 + 我复算的 `r3-full-revert`，共 **4 次一致**）。

**三轮新增结论（把机制钉死的一步）：**

- **脚本全回退到 HEAD + 交付态 catalog → `963ebf88…`（我独立复现二轮的 X3）**：
  这证明**触发条件是 catalog 的存在，不是脚本的内容**。二轮的 `X3`/`X3b` 驱动脚本没保留，
  我用自己的脚本重跑了一次（runId `20260918-153000-t11r3-X3-repro`，构建 `BUILD SUCCESSFUL`，
  三个脚本的 sha256 在构建前实测为 `e35b51c2…`/`5af0e790…`/`8906b7ac…` = HEAD 字节）。
- **`E-C`（只追加一行注释）→ 仍是 `963ebf88…`**：纯注释不改变 blob。说明改动**不是**「任何 catalog 字节变化」。
- **`E-C2`/`E-C3`（在交付态 catalog 上**再**加一个未被引用版本项）→ `e2ff5421…`**（44,544,056 B），
  且两者**逐字节相同**（`0.0.1` 与 `9.9.9` 值不同、长度相同、得同一结果）。
  差异仍是**同样的 50 条条目**（49 lambda + 1 backport），blob 字符串长度 1,305,665 → 1,305,658（**−7**）。
- **`X5`（**整份** catalog 只有一条未引用版本项）→ `a84db151…`**（44,544,056 B，与 E-C2 **同一字节数**）——
  与 E-C2 **哈希不同**（尽管字节数相同），虽然「都是有一条未引用版本项」，
  但 X5 是**全新的文件**（没有交付态那 98 行的其余内容）。
  → **「catalog 的完整字节」都会进这个函数**，不只是「有没有多出一条 version」。
- **`E-C2` 是可复现的**：我用**逐字节相同的 catalog**（sha256 `4fdecb93…`）跑了**第二次**构建
  （`20260918-150000-t11r3-E-C2-rep2`），得到**同一个哈希 `e2ff5421…`**。
  → **该 blob 对 catalog 是确定性函数**，不是随机 —— 这与 `classes4/7/8.dex` 的
  非确定性（§5.7）**是两回事**，两者不可混为一谈。
- **E-C2 与 E-C3 的 catalog 字节不同**（`0.0.1` vs `9.9.9`，sha256 `4fdecb93…` vs `d96c5d71…`），
  却给出**同一个** `classes.dex`。说明进入这个函数的是 catalog 的**结构**（哪些键存在），
  而不是版本值的字面内容 —— 但**整份文件的其余字节**（X5 那条）**也会**进这个函数。
  这条只能如实写成「机制未完全定位」，**不要**据此断言「值无关」。

### 5.5 根因结论（一句话口径）

> **该 blob 的取值是「构建配置输入字节」的函数** —— catalog 的**有无与内容**都会改变它
> （无 catalog → `36b957ce`；交付态 catalog → `963ebf88`；最小 catalog → `a84db151`；
> 交付态 catalog + 一个未引用版本项 → `e2ff5421`），**与脚本内容无单调关系**
> （X3/X3b 把脚本全回退到 HEAD 但保留 catalog，仍是交付态哈希）。
> **已隔离到构建配置输入，机制未完全定位**（D8 是那个写入者，但决定 value 的确切输入未解析到）。

**已排除项（逐条有实验支撑）：**

| 排除 | 依据 |
|---|---|
| 依赖坐标差异 | §4.1：坐标逐字节一致，blob 仍不同 |
| 声明顺序 | catalog 的 alias / 依赖书写顺序未变，blob 仍随 catalog 字节变 |
| 脚本内容单独作用 | X3/X3b：脚本全回退到 HEAD + catalog 存在 → 仍是交付态哈希 |
| `clean` 陈旧 | X4b / X3b（`clean` 后重跑）与不 clean 的 X4 / X3 结果相同 |
| 构建非确定性（**对 `classes.dex`**） | 交付态组 **10 次构建哈希全同**（含我复现的 X3-repro）、回退态组 **5 次全同**；E-C2 用**逐字节相同的 catalog 复跑第 2 次**仍得 `e2ff5421…`（输入决定，非随机） |
| blob 的 value 由版本值的**字面内容**决定 | E-C2（`0.0.1`）与 E-C3（`9.9.9`）catalog 字节不同、得**同一** dex |

**未排除 / 已知盲区：**

- value 的确切算法**未定位**（已试 `String.hashCode(key)`、crc32、adler32、sha1/md5 前缀，全部不中）。
- 进入该函数的**确切输入面**未完全解析：X5（整份 catalog 只有一条未引用项，44,544,056 B）
  与 E-C2（交付态 catalog 再加一条，**同样** 44,544,056 B）**字节数相同但哈希不同**，
  说明函数吃的不止「有没有多余的 version 键」。
- `classes4/7/8.dex` **存在跨构建的非确定性**（见 §5.7），与 `classes.dex` 的「输入决定」
  **不是同一个现象**，两者不可混为一谈。

### 5.6 关于「50 条」的口径（不许缩写成「一条字符串」）

那条 blob 在字符串表里确实只是 **1 条字符串**，但它**内含 17,891 个条目、其中 50 个哈希变了**。
任何描述都必须同时给出这两个数字；写「只有一条字符串不同」而不提 17,891/50 是**严重误导**（二轮的错）。

## 10. 风险与回滚

### 10.1 行为变化（对用户可见）

- **无**。这是一次纯配置搬迁：解析坐标不变、产出 APK 的版本号与标识不变。
- 唯一的**新增**保护是「版本身份文件缺失/非法时在配置阶段直接失败」——这是把原先
  「写死字面量所以永远不会错」换成「从文件读所以必须校验」，失败是**更早、更响**的失败。

### 10.2 已知风险

| 风险 | 缓解 |
|---|---|
| `gradle/version.properties` 与 `libs.versions.toml` 是两个文件 | 各自的顶部注释写明边界（发版号 vs 依赖版本）；T11.md §3.4 固化 alias 方案 |

### 10.3 回滚

- **完全可回滚**：删除 `gradle/libs.versions.toml` 与 `gradle/version.properties`，
  `git checkout -- build.gradle.kts app/build.gradle.kts release-probe/build.gradle.kts`
