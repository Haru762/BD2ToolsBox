- `Test-Bd2UnitAll` 与 `Test-Bd2Unit` 同判据：跑前把 test-results 移入回收站、

  （`--expected-abi` + 资源名 + DEX 键名）、`audit_native_abi.py`。

### 2.3 实现过程中修掉的真实缺陷

1. **`LocalAll` 原先逐类调 `Test-Bd2Unit`** —— 每个类一次 Gradle，66 个类把同一个任务重跑
   几十次。新增 `Test-Bd2UnitAll`：每个 flavor 一次 Gradle + 一次 XML 聚合，判据不变。
   逐类入口保留（各任务要按类引用具体证据）。
2. **`Read-Bd2UnitXml` 的返回形状用错**：它是**扁平**聚合

## 2026-10-13 补：交付记录与冻结基线分开核对

## 2026-10-13 补：干净构建与「什么才是可复现的身份」

计划要求「在隔离环境做一次干净构建，核对产物版本、文件清单、字节/哈希与签名/时间戳，
产出的报告字节级可复现」。做下来发现**字节级不可复现，但内容级可复现** ——
这个区分很重要，弄错会把「同一份内容」判成两份不同的包。

### 做法

`tools/verify_clean_build.py`：记下当前两个 ABI release 的哈希 → `gradle clean`
（并**确认产物真的不在了**，不靠「命令返回 0」当作清干净）→ 从零重建 → 逐项比对。

### 实测（4 次 clean + 重建）

| 项 | 结果 |
|---|---|
| ZIP 条目数 | 163 → 163（一个不多、一个不少） |
| ZIP 条目的名字 / 未压缩字节 | **完全一致**（`entryManifestIdentical = true`） |
| **内容哈希** `contentSha256` | **完全一致**（arm64 `58593211…`、x64 `8c4f06f8…`） |
| **APK 文件哈希** `sha256` | **每次都不同** |
| 文件字节数 | 相同（arm64 22,693,546 / x64 22,865,631） |
| 构建耗时 | clean 4.6 s + 重建 120.2 s |

### 差异在哪里（定位过）

- 差异全部落在 **APK Signing Block**（最后一条 ZIP 条目与中央目录之间那 12,304 字节），
  ZIP 条目区一个字节都没变；
- 差异是 **31 段、每段 100–400 字节**，符合签名/摘要材料的形状，**不是**时间戳字段；
- 签名算法是 **RSA / SHA-256**（在 APK 里查到 `rsaEncryption` 与
  `sha256WithRSAEncryption` 两个 OID，`ecPublicKey` 与 `ecdsa-with-SHA256` 均为 0 命中），
  所以**不是** ECDSA 的随机 nonce；
- 只用了 **v2** 方案（v1/v3/v3.1/v4 都是 false）。

即：内容一样、签名块字节不同。根因在构建工具侧，本轮没有继续往下挖
（继续挖对交付没有增量价值，且已超出 T60 的范围）。

### 由此定下的规则

新增 `tools/apk_identity.py`：`contentSha256` = ZIP 条目（按名字排序）的名字 +
解压字节的 SHA-256。它与压缩方式、ZIP 写入顺序、签名块都无关。

- **`contentSha256`** → 「这次交付的是什么内容」的**身份**，可复现，用于核对重建；
- **`fileSha256`** → 构建实例相关，只用于校验「用户手上那份包没被改过」。

`artifact-manifest.json` 的 `t61Delivery` 两者都记；`verify_manifests.py` 对带
`contentSha256` 的条目核**内容哈希**（`hashKind = apkContent`），文件哈希降为参考信息
—— 否则每重建一次就会报一次假失败，把人训练成忽略这个检查。
