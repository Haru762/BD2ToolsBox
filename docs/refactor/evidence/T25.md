## 1. 本轮做了什么

### 1.1 新增 `core/operations/OperationRecovery`

- `classify()`：按 journal 文件顺序、分 operationId 把所有操作分成四态：
  - `Interrupted`：只落写前意图（`TARGET_REPLACING`）、没有确认替换 —— 中断；
  - `NeedsReconciliation`：已确认替换（`TARGET_REPLACED`）但后续无 `LEDGER_COMMITTED` —— 待人工核对/补账；
  - `Committed`：替换 + 提交都已落盘（窗口已闭合，journal 只是没被清）—— 无需动作；
  - `Unknown`：journal 读不出来/自相矛盾 —— 不能自动动作。
  - **只读 journal，不自动重放安装步骤、不改账本、不碰游戏文件。**
- `isCleanupPathAllowed(candidate, allowedRoots)`：清理路径必须严格位于某个允许根之内
  （用 `canonicalFile` 解析 `..`/符号链接/相对路径，再做**路径分量**包含性判断，
  不是字符串前缀）。防伪造/过期 journal 路径导致边界外递归删除。
- 与既有 `OperationJournalStore.recoveryVerdict()` 的区别：那条只回答「有没有待核对」，
  本类进一步区分「中断」与「已替换待核对」与「已提交」，供 UI 明示中断与下一步。
