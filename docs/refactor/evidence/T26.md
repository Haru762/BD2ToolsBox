### 2.1 为什么用**系统通知**当观测点

通知是**系统**持有的事实，不是我们自己的内存状态。用它当判据可以排除
「我自己的变量说它还在」这种自证。Binder/Job 的释放另有
`ShizukuConnectionLifecycleTest` 与 `OperationCoordinatorTest` 覆盖。

### 2.2 为什么刻意**不经过 Activity**

计划的核心验收是「任务中销毁界面再进入可观察同一任务」。这一层的前提是
**任务状态的所有者是 Service 进程级的状态，不是 Activity/ViewModel 实例**。
所以本类从头到尾不创建 Activity —— 拿不到 Activity 还读得到，才说明状态没挂在界面上。

### 2.3 用例

| 用例 | 断言 |
|---|---|
| `allThreeHostsExposeProcessWideStateObservableWithoutAnActivity` | 装入与扫描的通知**同时在场**且 id 互不相同 —— 它们不是共用一个状态位，不会互相踩 |
| `progressSurvivesRepeatedStartsLikeARecreatedUiWouldDo` | 跑到 7/10 后再 start（total 报 99）不得重置进度 |
| `stoppingEachHostRemovesItsOwnNotificationOnly` | 停装入收掉装入的通知，**但不动扫描的** |
| `cancellingPrepackRemovesItsNotification` | 取消预解包后不留常驻通知（留一个永远转的通知等于骗用户「还在跑」） |
| `startReportsWhetherTheForegroundServiceWasAccepted` | `start()` 返回 false 时**不留常驻通知**；返回 true 时通知必须真的在场 |
| `aRunningHostDoesNotLetASecondTaskTakeTheSameTarget` | 宿主在跑时协调器拒绝同目标的第二个任务，并说清被谁占着 |
