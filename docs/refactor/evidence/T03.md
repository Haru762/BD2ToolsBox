## 4. APK 条目级核验与整包哈希差异的归因（本项核心）

### 4.1 观测

历史包与重建包**字节数完全相同**，但整包 SHA-256 不同。逐条目比较结果：

| 项 | arm64-v8a | x86_64 |
|---|---:|---:|
| 条目名集合一致 | 是 | 是 |
| 条目数（双方） | 189 / 189 | 188 / 188 |
| 载荷逐字节相同的条目 | 186 / 189 | 185 / 188 |
| 载荷不同条目 | **3** | **3** |
| 压缩载荷差 | **−1572** | **−1572** |
| local header 区（含对齐填充）差 | **+1572** | **+1572** |
| EOCD 逐字节相同 | 是 | 是 |
| 中央目录差异 | 12 段 / 30 字节 | 12 段 / 30 字节 |

载荷不同的**恰好是同三条**：

```
META-INF/version-control-info.textproto
assets/chaquopy/app.imy
assets/chaquopy/build.json
```

### 4.2 三条条目的具体差异（已独立复算）

**① `META-INF/version-control-info.textproto` —— 构建机 git 元数据**

| | 字节 | SHA-256 | 内容 |
|---|---:|---|---|
| 历史 | 120 | `4afb6cc42bda673c95415ce06fc60caf3704b0fd9ca4892573cf0d32f91f8ed3` | `repositories { system: GIT; local_root_path: "$PROJECT_DIR"; revision: "0edab00c48e18bf4af6b6e8904c4468ee3fc889d" }` |
| 重建 | 42 | `577a29846b9d2ab88f013ed5ce0cc75355d4cfbef540ef637c49c95d233c236f` | `generate_error_reason: NO_VALID_GIT_FOUND` |

> 附带发现（供 T12/T13 参考，**不是本轮结论**）：历史 0.2.16 包里记录的是
> `0edab00c…`，即 **v0.2.15 的提交**——历史包是在 v0.2.16 提交之前构建的。
> 重建时因 worktree 未被 AGP 识别为有效 git 仓库而记录了 `NO_VALID_GIT_FOUND`。

**② `assets/chaquopy/app.imy` —— Chaquopy 导入归档**

| | 字节 | SHA-256 | 内部条目数 |
|---|---:|---|---:|
| 历史 | 6326542 | `29aa5af92972e3d06b46b88e3a30dca4a3257e0e3372b4eba12b23134df82096` | 164 |
| 重建 | 6325044 | `3495672d06bb7bcef372ffa81a69c0aa7b1932159ed19fd05c0591ca654b8ca6` | 152 |

内部差异**全部是构建环境差异，没有一处源码改动**：

- **多出 12 条空 `__pycache__/` 目录条目**（仅历史侧）：`__pycache__/`、`repacker/`、
  `utils/`、`vendor/UnityPy/` 及其 `classes/`、`classes/legacy_patch/`、`enums/`、
  `export/`、`files/`、`helpers/`、`resources/`、`streams/` 共 12 处。
- 152 条共有条目中 **16 条 CRC 不同**，其中 **16 条全部**在 `\r\n`→`\n` 归一化后
  逐字节相同，**真正内容不同者 0 条**。这 16 条是 15 个 Python 文件
  （`catalog_indexer.py`、`catalog_parser.py`、`cdn_downloader.py`、`character_scraper.py`、
  `local_bundle_indexer.py`、`main_script.py`、`maintenance_info_pb2.py`、
  `repacker/json_to_skel.py`、`repacker/repacker.py`、`resolver.py`、`spine_merger.py`、
  `unpacker.py`、`utils/__init__.py`、`utils/atlas_operations.py`、`utils/file_operations.py`）
  加 `vendor/UnityPy/LICENSE`，差异为 **LF ↔ CRLF**。

**③ `assets/chaquopy/build.json` —— Chaquopy 构建清单**

两侧同为 2927 字节；历史 `e8312940a16dc11bdf9fe66f47a60c00078dc8bd5c0f6dd8ef6371ec04307c1b`，
重建 `35db8fcfb6a321e6a9ff4e4e55f8fff7b62c482b811807bf55f32e9416574f1d`。
逐 JSON 指针比较后**唯一差异点是 `$.assets.app.imy`**——即上一条的派生结果。

### 4.3 归因结论

> **整包 SHA-256 不同的原因是构建环境差异，不是源码或 R8 输出差异。**
>
> 三条差异共使内含载荷缩小 **1572 字节**（app.imy −1498、version-control-info −73、
> build.json −1）；Android zipalign 的**全零 local-extra 对齐填充恰好增加 1572 字节**，
> 精确补偿，因此 local region / Signing Block / Central Directory / EOCD 的 offset 与
> size **全部不变**、EOCD 逐字节相同、文件长度相同，而内部哈希与整包 SHA-256 改变。
>
> 签名块本身 8192 字节（v2 `0x7109871A` 1402 + PKDS `0x504B4453` 4904 +
> Brew 填充 `0x42726577` 1854）：v2 与 PKDS 内容随内容摘要变化，
> **Brew 填充跨包哈希完全相同** `b78dd55d8821fc1609fd3c28b264bf24cae1bce00a704f42a721fde7b471d224`。

**直接佐证**：`classes.dex` 在历史与重建包中**逐字节相同**
（2877404 字节，SHA-256 `5e6403de77cc3eb9e76af29a6e49aae981f6a9baba2cdc7174e028132a4013b6`），
`mapping.txt` 两侧哈希完全相同。R8 的产物没有变化。

**约束：不得把历史/重建的差异归因于 R8。** 这与 §2.1「不能把历史 debug/release 差值
全归因于 R8」的要求一致，并且本轮给出了正面证据。

### 5.1 自检：退出码只由独立量决定（2026-09-15 审查后重写，见 §13）

`classify_content.py` 的退出码**不再**由「三项之和 = 实测总量」决定 —— 那两边是在
**同一个循环**里累加的，恒真，永远不可能失败。现在参与判定的四项都取自分组之外：

| 检查 | 独立来源 |
|---|---|
| `eocdEntryCount` | EOCD 记录里声明的条目数（裸字节解析）vs `zipfile.infolist()` 的长度 |
| `localRegionAccounted` | Signing Block / 中央目录偏移给出的 local 区字节数 vs 在每个 local header 处**实读**的 `30 + nameLen + localExtraLen + compressSize` 之和 |
| `groupEntrySum` | 分组条目数之和 vs 上述 EOCD 声明数；且任何条目都必须落进某个分组 |
| `regression` | 各组 `entries`/`compressed`/`raw` vs 已提交的 [baseline.json](baseline.json) 冻结值（`--expect`） |

五个包、四项**全部 PASS**，退出码 0。原来的三项之和检查降级为 `internalConsistency`，
**如实打印但不参与判定**。

**已做反证**（确认它能真的失败，而不是换个说法的恒真）：

- 把 Chaquopy 谓词改成 `assets/chaquopyTYPO/` —— 悄悄把 20.8 MB / 34 条挪进
  Other assets，任何总量都不变 —— `regression` 立即 **FAIL、退出码 1**，并逐组打印
  `Chaquopy entries expected=34 actual=0`、`Other assets compressed expected=23582 actual=20821627`。
- 把 EOCD 里声明的条目数改 +1：`eocdEntryCount` 与 `groupEntrySum` **双双 FAIL、退出码 1**。

两次反证中 `internalConsistency` 都仍报 `True`，正说明它没有鉴别力 —— 这也是它不再
参与判定的原因。

其中最关键的是**真实 release 的混淆快照形态** `files/mod_list_snapshot.json`

`MainViewModel.ModListSnapshot.savedAt` / `.mods` / `.sourceDirs`，
**`version` 字段在历史 release 中根本不存在**。内容只含测试目录
（`dhz_test`、`scan0211-lifecycle-a7f3c9`），无用户身份。

**必须如实写明：这份快照当前会被 loader 丢弃，不能记作「可读」。**
R8 重命名了字段，`ModListSnapshot` 读的却是 `version`/`savedAt`/`mods`/`sourceDirs`
（快照顶层实际键为 `a`/`b`/`c`）：

- `MainViewModel.kt:3077` 要求 `snapshot.version == SNAPSHOT_VERSION`（常量 = 1，`:106`）。
  JSON 里没有 `version` 键，而 Gson 用 `Unsafe` 造实例、**不走 Kotlin 默认值**，
  `Int` 字段落成 `0` → 命中该分支，`Log.i` 打印「快照版本 0 不是 1，丢弃」后
  **显式 `return emptyList()`**（`:3079`）。这是**刻意写的版本闸门，不是异常兜底**。
- 即便版本号对上，`MainViewModel.kt:3081` 还要求
  `snapshot.sourceDirs == _modSourceDirs.value`，缺失字段落成 `null`，同样 `return emptyList()`。
- `MainViewModel.kt:3084` 的 `snapshot.mods.mapNotNull{...}` 是**第二道防线**：`mods` 缺失时
  Gson 会给 `null`，解引用即 NPE，由 `:3085` 的 `catch`（`:3086` 打印
  「冷启动快照读取失败，按没有快照处理」）兜成 `emptyList()`。

三条路径都通向 `emptyList()`，即**当作没有快照**；其中第一条是**主要**路径，且是显式判定。
**这是从源码与 JSON 形状推出的结论，本项没有执行 Kotlin loader 来实跑**（那需要构建，
超出 T03 的只读范围）——按「不以预期代替结果」的要求，这里标明它是推断而非实测；
逐条依据（文件:行号）如下表，供复核。

## 9. 可复现性

本项把一次性脚本提升为**仓库内工具** `tools/apk-baseline/`（6 个脚本 + README + 驱动脚本），
满足验收「同一份 APK 的哈希和条目分类可重复计算」：只读、仅标准库、不硬编码本机路径、
分类脚本带自检并在失败时返回非零。

- **不依赖工作目录**：驱动脚本的 `-Root` 默认由 `$PSScriptRoot` 上溯两级得到，
  传给每个工具的路径**一律绝对**；`classify_content.py` 的回归判据读已提交的
  `baseline.json`（`--expect` / `--expect-package`），故换机器、换 cwd 结果相同。
- **失败即非零**：分类脚本的回归判据有实测反证（§5.1）——弄错分组谓词或篡改 EOCD
  都会 `exit 1`；驱动脚本任一步非零即整体 `exit 1`。

一次性核验期间曾使用的 `sigdetail.py`（v2 signer 明细解析）**在真实包上抛
`struct.error`，已删除**，不在仓库里留必然崩溃的工具。`structure.py` 内的同类解析路径
在真实包上同样失败，但它是**静默降级**而非「记录了错误」：失败只被塞进一个本地 dict 的
`parse_error` 键（`structure.py:105-106` 写入），该键**既不打印也不序列化**；下游比较块以
`if pra.get("parsed") and prb.get("parsed")` 为前提（`structure.py:187`），解析失败时整段被跳过。
因此**签名与证书一律以 `apksigner` 为准**，见 §3；`structure.py` 仅在两侧都能解析成功时给佐证。
该限制已写入 `tools/apk-baseline/README.md`。

### 9.1 与 brief「执行/验证命令」的偏差（如实登记）

brief 第 25-32 行给出的三条命令，本项处理如下：

```powershell
. (Join-Path $Root 'tools/verification.ps1') -ProjectRoot $Root                     # 未执行
Get-FileHash -Algorithm SHA256 -LiteralPath (.../app-arm64-v8a-release.apk)         # 已执行（§1 表内两个 ABI 的哈希）
Show-Bd2Dependencies                                                                # 未执行
```

未执行的两条不是图省事，而是与 T03「只读、不构建、不动设备」的约束相抵：

- `. tools/verification.ps1` 是**点源**，会在**调用方会话**留下副作用：`:28` 执行
  `Set-Location -LiteralPath $Root`（改掉调用者 cwd），`:44` 向调用者注入 `$env:JAVA_HOME`。
  且它是 T02 引导版，`$Mode -ne 'Load'` 时仍 `throw`（`:90-92`），`LocalAll` 要到 T04 才有实现。
- `Show-Bd2Dependencies` 会调 Gradle（`:75-88` 的 `:app:tasks --all` 与 `:app:dependencies`），
  属构建系统操作，会写 Gradle 缓存，不在「只读分析已存在的 APK」范围内。
- T03 真正需要证明的是**同一命令可重复算出相同的哈希与分类**，这已由 §2 的 18 步驱动脚本
  与 §5 的 `--expect` 回归判据（带反证）覆盖。

该偏差与 `verification.ps1:50` 的 `Invoke-Bd2Gradle` 未显式传 `-p $Root`（因此依赖 cwd）
一并作为移交项，留待 **T04** 收敛。
