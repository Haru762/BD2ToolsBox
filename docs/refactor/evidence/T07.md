### 3.3 `ShizukuFileService.kt`（主战场）

**`copyStream` 改为经 `AtomicFileWriter` 提交**（下面是**二轮整改后**的最终形态）：

```kotlin
private fun copyStream(source: File, dest: File, allowEmptySource: Boolean = false) {
    val expectedSize = source.length()
    AtomicFileWriter().write(
        target = dest,
        verifyBeforeCommit = { staged ->
            val written = staged.length()
            if (written != expectedSize) {
                throw IOException("暂存文件字节数与源不一致（源 $expectedSize，暂存 $written）：${source.path}")
            }
            if (written <= 0L && !allowEmptySource) {
                throw IOException("暂存文件为空，拒绝提交：${source.path}")
            }
        }
    ) { output ->
        source.inputStream().use { input -> input.copyTo(output) }
    }
}
```

**签名的改动只有一处：新增 `allowEmptySource` 参数**（默认 `false`，保持单文件路径的
原语义）。`copyFile` 走默认值，`copyTree` 显式传 `true`。

> **一轮的形态与它的问题（保留原文 + 反证）**：一轮里这条规则是**无条件**的
> （`if (written <= 0L) throw`，无参数），而 `copyTree` 对目录树里**每个**文件都调
> `copyStream` —— 于是树里任何一个合法的 0 字节文件（Android 上惯例的 `.nomedia`
> 就是 0 字节）都会让整个 `copyDirectory` 失败，连非空的那个文件也不落地。
> 这是**复核者 R3 的对照实验**拓出来的真缺陷 #2（§8.9 有完整证据），
> 二轮按编排者裁定 3 收窄为「只对单文件路径生效」。**收窄的依据**：
> 「防止目标被截断」这件事已经由同目录暂存 + 原子替换保证，
> 「空源拒绝」对目录树里的普通文件没有安全收益、只有失败面；
> 而在单文件路径上它仍然必要（空源顶掉游戏目录的 `__data` 却报成功）。

校验用 `length()`，**不把文件读进内存**（§2.4）。

**顺带受益的只读路径**：`executeBundleScan`（扫游戏 bundle → 缓存里的 `tempDataFile`）
与 `copyLocalBundleToCache` 也走 `copyStream`，所以它们现在也不再可能留下半写的临时文件。
这是同一条改动的**副作用**，不是单独修的 —— 我把这条写在这里而不是当成已验收项。

`copyDirectory` 加了文档注释，明确「**这不是事务**」（见 §4.2 的部分成功）。

### 3.4 `AtomicFileWriter` 的 API 契约（计划原文，固定）

```kotlin
class AtomicFileWriter {
    fun write(
        target: File,
        verifyBeforeCommit: (File) -> Unit = {},
        write: (OutputStream) -> Unit
    )
}
```

**逐条对照计划验收要求：**

| 计划要求 | 实现 | 依据 |
|---|---|---|
| 写目标**同目录**的独占临时文件 | `File.createTempFile(PREFIX, SUFFIX, dir)`，`dir = target.parentFile` | §6.0 探针（`stagingFileLivesInTheTargetDirectory…` 用例钉住） |
| 完成大小/内容校验 | `verifyBeforeCommit(staged)` | §6.0 |
| 与**可支持的**同步 | `syncIfSupported(out)`：`fd.sync()`，`SyncFailedException`/`UnsupportedOperationException` 降级放行 | §6.0 的 G 行（宿主）+ §7.2（设备侧未单独断言，没有标成已覆盖） |
| 校验发生在**替换之前** | `verifyBeforeCommit` 在 `moveIntoPlace` 之前调用 | §6.2 证伪 B（挪到之后 → 红 5 条） |
| 失败**抛原始错误**、目标保持旧内容 | 不 catch、不包装；`committed` 标志控制 finally 清理 | §6.1 证伪 A |
| 文件系统不支持提交语义时**安全失败** | 捕 `AtomicMoveNotSupportedException` → 抛 `IOException`，**不**退化 | 代码核对；FUSE 上**未触发过**，见 §7.2(d) |
| 新建目标（此前不存在）的**权限值** | 同目录已有普通文件 → 照抄其 mode；没有可参考的才退回父目录 rw 位（屏蔽执行位），**不是**硬编码 | `newTargetInheritsSiblingFilePermissionsOnRealFuse` + `newTargetFallsBackToParentDirectoryPermissionsWhenDirectoryHasNoPlainFiles`（设备）+ `selectReferenceFile*` 三条（JVM）+ §6.7 证伪 J |

| **不许整份读进内存** | 校验用 `length()`；接口给的是**文件**不是字节 | §2.4 |

### 3.5 `BackupGate.kt`（D5 授权的落点）

三个调用点改走同一个纯函数，**不各自判断**：

```kotlin
enum class BackupGateDecision { PROCEED, ABORT, PROCEED_WITH_WARNING }

fun decideBackupGate(
    backupEnabled: Boolean,
    backupSucceeded: Boolean,
    onCommitPath: Boolean
): BackupGateDecision = when {
    !backupEnabled -> PROCEED
    backupSucceeded -> PROCEED
    onCommitPath -> ABORT
    else -> PROCEED_WITH_WARNING
}
```

三态而不是布尔：「放行但必须上报」与「放行且无需上报」**必须可区分**，
否则调用方无从表达「备份失败了」（`proceedAndProceedWithWarningAreDistinguishable`
把这条钉住）。用布尔就是 T07 之前「三处丢弃返回值」的同一个坑换个位置。

> 而那条用例一个字都没碰权限（复核者把它改成 `rw-------`，11/11 仍全绿）。
> 二轮的重写规则：**只写用例里能指到具体断言行的事实**。

> **一处自我参照的坑（二轮自己抓到的，记在这里以免下次再犯）**：新用例初版把期望值
> 写成 `AtomicFileWriter.maskExecutableBits(parentPermissions)` —— 也就是**用被测代码
> 自己算期望值**。
>
> **它为什么是弱点（要说准）**：这个写法**能**抓住「新建分支改回硬编码 0644」
> （E 的第一次 `runId=20260917-190147-…` 确实红了）—— 因为那时调用侧不再走
> `maskExecutableBits`，两边的值真的不同。但它**抓不住「翻译规则本身被改坏」**：
> 那种破坏下输入与期望会一起变，断言恒真。也就是说这条断言只守住了两层里的**一层**，
> 而它看上去像守住了全部。
>
> **改法**：期望值换成与实现无关的**字面量**（父目录由用例显式设为 `rwxr-x---`，
> 故期望写死 `rw-r-----`），于是设备用例守住「端到端实际取值」这一层；
> 翻译规则那一层由 JVM 的 `maskExecutableBitsKeepsReadWriteAndDropsExecute` 守
> （期望写死 mode 字符串）。**两层各自独立，任一层被改坏都会有对应的断言红。**
>
> **三轮的延伸（同一个坑的第二处）**：三轮把规则改成「优先抄同目录文件」之后，
> 期望值写死 `rw-r--r--`（二轮那版）**不够了** —— 它只描述回退分支。
> 现在的期望是「兄弟文件的 mode」（0664，用例自己设的），
> **并额外用一条 JVM 用例钉住「挑的是哪一个文件」**（名字序、跳过暂存件、跳过目录）。
> 这样「端到端取值」「挑谁」「怎么翻译」三层各有一条断言。

getPosix=rw-rw----          <- app 在该卷上新建文件的权限
setPosix=OK                 <- 该卷支持 setPosixFilePermissions
after=rw-r--r--             <- 设成 rw-r--r-- 后读回一致
tempfilePerms=rw-rw----     <- File.createTempFile 建出来的暂存件权限
```

**所以：暂存件是 `rw-rw----`（other 无读权限），不是 `0600`；该卷支持改权限。**
推论：不做权限搬运的话，一次提交会把 `__data` 悄悄降级成 other 读不到 ——
而 `__data` 是要被**游戏进程**（另一个 UID）读的。**这一步在设备上是活的防线。**
注释已按实测值改写。

**断言写错了一次**：初版用例断言「提交后必须 other 可读」，拿一个
`writeText` 建出来的（`rw-rw----`）目标去跑，`runId=20260917-052644-…` **真的红了**：

```
1) committedTargetIsReadableByOtherUids
AssertionError: 提交后的 __data 必须让 other 读得到（实测该卷新建文件是 rw-rw----），
实际 [GROUP_READ, GROUP_WRITE, OWNER_READ, OWNER_WRITE]
```

**那次红是对的、但断言写错了对象**：「目标本来是什么权限就保持什么权限」才是
这一步的契约，**不是**「一律放宽到 other 可读」。改为
`commitDoesNotDowngradeTargetPermissions`：显式先把目标设成 `rw-r--r--`，
再验提交**没把它降级**。这条在证伪 D 里真的红了（§6.4）。
#### 二轮整改：新建分支改成「继承父目录权限位」（编排者裁定 2）→ **三轮改成「优先照抄同目录文件」**

**一轮的写法与它的代价**：目标**不存在**时硬编码 `rw-r--r--`（0644）。当时理由写的是
「该卷上 app 新建文件拿到 `rw-rw----`（other 无读权限），而 `__data` 要被游戏进程读，
所以必须挑一个明确让 other 可读的值」。

**二轮实现的是「取父目录 rw 位、屏蔽执行位」，依据写的是「真实游戏目录是 2770
⇒ 新建得到 0660，与邻居一致」—— 那个依据是错的。** 二轮独立复核者在设备上实测，
三轮（2026-09-17）我又独立复测一遍，两次结论一致：

```
/storage/emulated/0/Android/data/com.neowizgames.game.browndust2                2770 drwxrws---
…/files                                                                         2770 drwxrws---
…/files/UnityCache                                                              2750 drwxr-s---
…/files/UnityCache/Shared                                                       2750 drwxr-s---
…/files/UnityCache/Shared/<bundle>/                                             2750 drwxr-s---
…/files/UnityCache/Shared/<bundle>/<hash>/                                      2750 drwxr-s---   <- 新建 __data 的父目录
```

三轮复测的**分布**（只读 `find … -exec stat`）：

| 统计 | 实测 |
|---|---|
| `Shared/` 下的 hash 目录 | **1830 个，全部 2750，0 个 2770** |
| 全树目录（`find <gameRoot> -type d`） | **3689 个：2750 有 3666 个，2770 有 23 个** |
| 那 23 个 2770 在哪 | 游戏根、`files/`、`files/VideoData`、`files/SoundData`、`files/Neo`、`files/DBFiles` 等 —— **全部与 `__data` 无关** |
| `__data` 文件本身的 mode | **0660（`rw-rw----`）**；同一个 hash 目录里还有 `__info`，也是 0660 |
| 每个 hash 目录里的普通文件数 | **2**（`__data` + `__info`），抽 400 个目录逐个核过，无一例外 |

**所以二轮那条规则在真实路径上给出的是 `rw-r-----`（0640）**（2750 屏蔽执行位），
而真实 `__data` 是 `rw-rw----`（0660）—— **group 位少了写权限**，新建的那份会成为
同目录里**唯一** group 不可写的文件。**「与邻居一致」这个理由在真实路径上不成立。**

**三轮的最终规则**（编排者按用户裁定选定的 (b)，`AtomicFileWriter.newFilePermissions`）：

| 目标状态 | 权限取值 |
|---|---|
| **已存在** | 照抄它自己的 mode（不变） |
| **不存在，但同目录里已有普通文件** | **照抄其中一个的 mode**（挑选规则见下）—— 真实路径上这就是 0660，因为同目录总有 `__info` |
| **不存在，且同目录里没有普通文件可参考** | 退回：父目录 mode **屏蔽执行位**（`dirMode and 0b110110110`）⇒ 目录 2750 → 文件 0640 |
| 连父目录都取不到 | 抛 `IOException` ⇒ **提交失败**（不硬编码 0644） |

**挑选规则必须确定**（`AtomicFileWriter.selectReferenceFile`）：候选中**只留普通文件**
（目录带执行位、不是参考形态），**去掉暂存件自身**（`write` 先建暂存件再搬权限，
此刻它就在同目录里，且点前缀在名字序里排最前 —— 不排除就会抄到它自己的默认权限），
然后**按文件名升序取第一个**。刻意不用 `listFiles()[0]`：那依赖文件系统返回顺序，
权限值会跟着飘、用例没法断言。

**两条分支各自在什么条件下出现（别把 0660 当成无条件结论）**：
真实游戏路径走第 2 条（目录里有 `__info`），得到 **0660**；目录为空时才走第 3 条，
得到 **0640** —— 后者**不在真实游戏路径上**，设备用例用一条独立用例把它钉住而已。

`setPosixFilePermissions` 抛 `IOException` → **提交失败**（不降级成警告）；
抛 `UnsupportedOperationException`（无 POSIX 概念的卷，如宿主 NTFS）→ **跳过**。
这两条一轮起就是这样，未改。

**为什么屏蔽执行位**（只对第 3 条回退路径有意义）：目录必须带执行位才可进入，
文件带执行位是另一回事（`__data` 是数据文件）。第 2 条抄的是普通文件，本来就不带执行位。

**这一格的守卫（三层，各自独立、覆盖不同的东西）**：

| 层 | 用例 | 守什么 |
|---|---|---|
| 设备（照抄同目录） | `newTargetInheritsSiblingFilePermissionsOnRealFuse` | 同目录有文件时**真的抄了它**（兄弟设 0664、父目录设 0750，两者可区分） |
| 设备（回退分支） | `newTargetFallsBackToParentDirectoryPermissionsWhenDirectoryHasNoPlainFiles` | 目录为空时才退回父目录 rw 位（0750 ⇒ 0640） |
| JVM（挑选规则） | `selectReferenceFilePicksLowestNameDeterministically` / `selectReferenceFileSkipsStagingFiles` / `selectReferenceFileIgnoresDirectories` | 挑选规则本身确定、跳过暂存件与目录 |
| JVM（翻译规则） | `maskExecutableBitsKeepsReadWriteAndDropsExecute` | 第 3 条的「目录 → 同组文件」翻译 |

**破坏实验**：把 `newFilePermissions` 改成**永远走父目录回退**（即取消「优先抄同目录」
这条本轮新增的路径）→ 设备套件 `Tests run: 13, Failures: 1`，红的是
`newTargetInheritsSiblingFilePermissionsOnRealFuse`（§6.7 证伪 J）。
二轮那两个形态（E2 硬编码 0644、E3 硬编码 0600）在**本条用例**下同样会红 ——
因为 0664 / 0644 / 0600 / 0640 四个值互不相同，一条断言同时钉住四种破坏形态。

      at android.widget.Toast.makeText(Toast.java:506)
      at …MainViewModel.toast(MainViewModel.kt:4039)
      at …MainViewModel.reportBackupFailure(MainViewModel.kt:1810)
    ```

## 10. 风险与回滚

**风险（按严重度）**

1. **`preservePermissions` 在真实链路上的行为未被验证**（§7.2(c)、§5.3）。
   我们证明了「app 自己的卷上，提交保持目标原权限 / 新建时设为 `rw-r--r--`」，
   但**没有**证明「shell UID 写进游戏目录后，游戏进程读得到」。
   这是本轮最大的一格不确定性。**缓解面**：即使这一步的效果不如预期，
   它也不会让情况比改动前更坏 —— 改动前 `dest.outputStream()` 走的是同一套
   umask，我们只是**显式**照搬/设定。
2. **暂存件的空间代价**：一次提交要额外占一份完整的 `__data`（26 MB 级，§2.4）。
   装入时若设备空间紧张，本来能勉强成功的拷贝现在可能因 ENOSPC 失败。
   **这是刻意的取舍**：宁可失败且保留原版，也不要留下半截文件。
   但它是**用户可感知的行为变化**（原本「勉强能装」，现在「装不下」），
   而 §7.2(b) 说明这条路径**没有真实 ENOSPC 下的实测数据**。
3. **`AtomicFileWriter` 的暂存件残留累积**（§8.3）。进程被杀时留一份，
   没有清理策略。极端情况下（Shizuku 服务反复被杀 + 反复装入）会累积占空间。
4. **`Interrupted` 不能中止拷贝**（§6.0 第 10 格实测）。所以「取消」的响应
   是**等当前文件提交完**才生效的，而一个 26 MB 的拷贝要跑一会儿。
   这符合计划「提交临界区完成后再响应取消」，但对用户来说「点了取消没立刻停」。
5. **`backupPristineOriginal` 的行为变严**：提交路径上备份失败现在会**跳过该目标**。
   改动前它会继续覆盖（丢掉原版）。所以用户可能看到「本来能装上的现在不装了」——
   这是我们**有意**换来的（宁可这次不装，也不要原版永久丢失）。
6. **二轮引入的变更（相对一轮，需要编排者知悉）**：
   - **新建 `__data` 的权限位变了**（三轮整改后）：一轮硬编码 `rw-r--r--`（0644）；
     二轮改成「父目录 rw 位」；**三轮改成「优先照抄同目录里已有的普通文件」**。
     真实游戏路径上（`Shared/<bundle>/<hash>/` 里总有 `__info`）得到的是
     **`rw-rw----` / 0660** —— 与同目录已有的 `__data` / `__info` **逐位相同**。
     **注意这是「该目录有普通文件时」的结果**：目录为空时会退回「父目录 rw 位」
     并得到 `rw-r-----`（0640）—— 真实游戏路径上不会出现这个分支（三轮实测
     400 个 hash 目录、每个都有 2 个普通文件）。
     **代价**：若某台设备上游戏进程需要 other 位才能读**新建**的 `__data`，
     0660 会比 0644 更容易读不到。但真实游戏目录里**已存在**的 `__data` 本来就是 0660
     （三轮实测：`__data` 样本 300 个全部 0660），所以 0660 才是「与现状一致」的选择；
     而且新建场景下目标此前不存在，没有「原有权限被别人依赖着」这回事。
     **这一格没有以游戏 UID 实测过**（§7.2(c)）。
   - **目录树里的 0 字节文件恢复为可拷贝**（一轮会让整棵树失败）。这是**放宽**，
     不新增失败面。
   - **`FinalInstallResult` 多了一个字段**（带默认值），既有构造点不受影响。

**回滚**：T07 的改动是**自包含**的 —— 二轮后是 7 个新建（含 4 个测试），6 处修改
（其中 `ModModels.kt` / `AppDialogs.kt` 是裁定 3 附加的授权范围内改动），
无 schema 变更、无持久化格式变更、无 AIDL 变更。
回滚即 `git revert` 提交，不需要数据迁移。具体地：

- `copyStream` 改回 `dest.outputStream().use { input.copyTo(it) }` → 行为回到改动前；
- `decideBackupGate` 的调用点删掉、恢复丢弃返回值（**不推荐**：那正是本项要修的缺陷）；
- `ShizukuManager` 的 `.version(6)` **必须跟着回滚到 5**，否则 Shizuku 会为一份
  与旧 dex 相同的实现再起一个进程（无害，但没意义）。

**没有「以直接覆盖作为兼容回退」这条路**：`AtomicFileWriter` 在
`AtomicMoveNotSupportedException` 时抛 `IOException` 而**不**退化成写目标，
这是计划落实要求第 1 条明令的。所以在一个不支持原子替换的卷上，
T07 之后**装入会失败**而不是「可能半途损坏」—— 这是刻意的行为变化。

### 11.0 补充设备证据：真实游戏目录上的端到端验证（2026-09-17，编排者执行）

**背景**：§7.2(c) 与 §8.8/§5.3 把「以 shell UID 写游戏目录后游戏进程读得到吗」标为
**未覆盖**。该设备上的 MuMu 已经装好并下完 BD2（18 GB / 1830 个 `__data`），
所以这一格可以补测。

**方法**：在**真实游戏目录**里取一个 30 KB 的 `__data`，用与 `AtomicFileWriter`
**逐步骤对应**的文件系统操作改写它（宿主侧没有 `setpriv`/`run-as`，无法用游戏 UID 直读，
所以判据用**文件元数据 + 游戏自身启动是否报错**）：

1. 同目录建暂存件（对应 `File.createTempFile(PREFIX, SUFFIX, dir)`）→
   实测拿到 `rw-rw---- root:ext_data_rw`；
2. `chmod 0660` 照搬目标权限（对应 `preservePermissions`）；
3. `mv -f 暂存件 目标`（对应 `ATOMIC_MOVE | REPLACE_EXISTING`）。

**目标文件**：`files/UnityCache/Shared/c7663e88…/802b0806…/__data`（内容先备份到
`/data/local/tmp/t07-target.bak`；改写前后 sha256 **逐字节相同**）。

| 项 | 改写前 | 改写后 | 结论 |
|---|---|---|---|
| 权限 | `rw-rw----` | `rw-rw----` | **不变** |
| 属组 | `ext_data_rw` | `ext_data_rw` | **不变**（靠目录的 setgid 位） |
| 属主 | `u0_a66`（游戏） | `root`（写入者 = Shizuku 的 UID） | **变为写入者** |
| 内容 | `00de6275…` | `00de6275…` | 一致 |
| inode | 3932319 | 3932403 | 原子替换换 inode |

**游戏随后启动的结果**：`[ON_DOWNLOAD_COMPLETE] loadedBundles=3` →
`IntroUI::OnDownloadComplete` → 连上 `chat.bd2.pmang.cloud:38501`，
**无 bundle / cache / CRC / 重下载相关报错**；被改写的那个文件也**没有**被游戏重写
（mtime 仍为改写时间，属主仍为 `root`）。
