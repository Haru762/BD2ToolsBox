## 2. 机器校验（R1–R7）

| 规则 | 触发条件 |
|---|---|
| R1 | `core/**` → `ui`/`feature` |
| R2 | `data/**` → `ui`/`feature` |
| R3 | `feature/**` → `ui` |
| R4 | `feature/**` 下非 Compose 且非 ViewModel 的文件 → `android.*`/`androidx.*` |
| R5 | `ui/viewmodel/**` → `androidx.compose.*` |
| R6 | ViewModel 构造器注入另一个 ViewModel |
| R7 | `ui/screens/**`、`ui/components/**` → `java.io`/`java.net`/`okhttp3`/`com.chaquo.*`/`core.engine`/`core.python`/`core.fileaccess`/`data.repository` |

设计取舍：R4 **按内容**判 ViewModel（不按文件名 —— 本轮就踩过一次误判）；
R7 只覆盖 `ui/screens`+`ui/components`（`ui/viewmodel` 是执行入口的合法持有者）；
`ALLOW` 逐条带理由，**没有全局忽略开关**，且有用例强制「每条 allow 都有非空理由」。

## 3. 首轮发现并修复的真实违规

```
R4 feature/cdk/CdkViewModel.kt: androidx.lifecycle.ViewModel
R4 feature/install/InstallExecutor.kt: android.util.Log
R7 ui/screens/CharacterScreen.kt: com.bd2toolsbox.data.repository.CharacterMetaRepository
```

| 违规 | 判定 | 处置 |
|---|---|---|
| `CdkViewModel` → `androidx.lifecycle.ViewModel` | **误报** | ViewModel 合法依赖 lifecycle；R4 改为「按内容识别 ViewModel 后豁免」 |
| `InstallExecutor` → `android.util.Log` | **误报但登记风险** | 仅一处失败路径日志，不是平台/UI 依赖；写进 `ALLOW` 并注明「该行在 mockable `android.jar` 下会抛 `Stub!`，这条失败路径当前无 JVM 覆盖」 |
| `CharacterScreen` → `CharacterMetaRepository` | **真违规（依赖边）** | 该导入只服务 KDoc 链接，实际不执行数据访问；删掉导入并把 KDoc 改成文件路径引用 |

修复后：**116 个文件、0 违规、1 条带理由的例外**。

另外修掉一个真实的反向依赖：`feature/cdk/CdkResultPresentation.kt`（Compose 文件）
放在 `feature/` 会让 `feature → ui` 成立 → 移到 `ui/components/RedeemResultComponents.kt`，
`feature/cdk` 只剩纯逻辑（`RedeemSummary`）与 ViewModel。

## 5. 物理模块化结论

**不拆分 Gradle module**（详见 `architecture.md` §4）：
逻辑边界已由 R1–R7 机器守住；拆物理 module 主要带来编译增量收益而非边界收益，
却会牵动 `verification.ps1` 的任务映射、`release-probe` 的跨包反射面与 R8 mapping 归档；
空 Gradle module 只是形式。**未来若迁 Python 模块，Chaquopy 仍只在一个模块实际应用**
（现为 `:app`；`:release-probe` 刻意不应用）。
