# T19 证据：隔离 Shizuku Binder 并由任务持有连接

- 本轮核对：2026-09-30（Asia/Shanghai），起点 `3c7749f`，分支 `refactor/android-architecture`。
- 当前状态：**IMPLEMENTED_NOT_VERIFIED**。x86_64 设备验收 + arm64 静态审计已过（T19 属 B 类，不要求原生 arm64 真机，见 [arm64-verification-policy.md](../arm64-verification-policy.md)）；未做真实 Shizuku 授权场景的设备验收（AVD/本机模拟器均无 Shizuku 服务）。
- 执行依据：[有效 TODO 的 T19](../../superpowers/plans/2026-09-15-android-refactor-todo.md)。

## 1. 问题与修复范围

**旧行为：** `ShizukuManager` 是全局 object，`MainActivity.onDestroy` 在 `isFinishing` 时无条件调用 `unbindService()`——页面销毁即无条件切断 Binder 连接，即使 `installScope`（进程级 scope，故意设计为活过界面销毁）里还有转换/装入/扫描任务在跑，也会被切断。

**修复：** 把"连接何时释放"从"页面是否结束"改成"是否还有客户端在用"：

1. 新增 `core/fileaccess/GameFileAccess.kt`：领域接口，方法签名对应旧 `ShizukuManager` 的游戏目录操作；新增 `acquire()`/`release(token)` 占用契约；`listGameBundles()` 返回 `DirectoryListingResult`（区分"确实为空"与"读失败"）而非旧的 `Map?`。
2. 新增 `core/fileaccess/ShizukuGameFileAccess.kt`：实现类，内部持有 `ConnectionOccupancy`，包装旧 `ShizukuManager` 的绑定/解绑逻辑；只在最后一个 token 释放时才真正 `unbindService()`。
3. 新增 `core/fileaccess/ConnectionOccupancy.kt`：占用计数抽成独立纯类（原因见 §3），JVM 可测。
4. 新增 `di/FileAccessModule.kt`：与 T18 的 `EngineModule` 同一模式——Hilt provider 委托到 `GameFileAccess.get()` 的惰性单例，不让 DI 与旧静态门面各自持有不同实例（否则占用计数分裂）。
5. 重写 `service/ShizukuManager.kt` 为委托门面：真正的绑定/占用生命周期全部转发到 `GameFileAccess.get()`；保留原有公开方法签名（`isRunning`/`copyLocalBundleToCache`/`installConvertedBundle`/`checkLocalBundles`/`executeBundleScan` 等），让散布在 `MainViewModel` 20 余处的旧调用点不必在本任务内全部迁移到新接口（T20 收尾时再迁移调用点、删除这个门面）；新增 `acquireConnection()`/`releaseConnection(token)`。
6. 修改 `MainActivity.kt`：`onCreate` 时 `acquireConnection()` 拿到 token，`onDestroy(isFinishing=true)` 时只释放这一份，不再无条件解绑；仍保留 `isFinishing` 判断（避免旋转屏幕时不必要的解绑/重绑，见代码注释）。
7. 在 `MainViewModel.kt` 里给 5 处活在 `installScope`（跨界面销毁）且真正触碰 Shizuku Binder 的入口接入占用：`confirmBundleScan`（扫描循环）、`processInstallJobs`（转换批处理）、`doInstallConvertedBundles`（直接装入）、`moveFilesToGame`（提交装入游戏目录）、`reconcilePendingInstalls`（核对恢复）。每处 `acquireConnection()` 后立即 `try`，`finally` 里 `releaseConnection(token)`。
8. AIDL 协议升级（`IFileService.aidl` 注释 + `.version(7)`）：`listBundleDirectoryPaged` 从裸数组改为 envelope（`{"ok":true,"entries":[...]}` 或 `{"ok":false,"error":"..."}`），修复"目录不存在/listFiles 返回 null/异常/确实为空"四种情况全部编码成同一个 `[]` 的问题。`ShizukuFileService.kt` 与两处客户端解析逻辑（`ShizukuGameFileAccess.listGameBundles`/`checkLocalBundles`）同步更新。

## 2. 为什么占用计数抽成独立类

`ShizukuGameFileAccess.unbindService()` 会真实触碰 `Shizuku` 类静态初始化（构造 `IShizukuApplication.Stub`，继承 `android.os.Binder`）。JVM 单测环境没有真实 Binder 实现，直接调用会抛 `Method attachInterface in android.os.Binder not mocked`。若把计数逻辑和 `unbindService()` 耦合在一起，就无法在 JVM 里独立验证"最后一个 token 释放才触发"这条核心契约。

把计数抽成 `ConnectionOccupancy(onAllReleased: () -> Unit)`——纯 Kotlin，构造时只接收一个回调，不引用任何 Android/Shizuku 类型；`ShizukuGameFileAccess` 用 `ConnectionOccupancy(onAllReleased = ::unbindService)` 组合它。

## 3. 已复现并修复的真实缺陷（自查）

**缺陷 1：`Set.remove()` 返回值未被使用。** 初版实现是：

```kotlin
fun release(token: Any) {
    activeTokens.remove(token)
    if (activeTokens.isEmpty()) onAllReleased()
}
```

`Set.remove()` 对不存在的元素返回 `false` 但不抛异常；`activeTokens.isEmpty()` 在**重复 release 同一个已经不在集合里的 token** 时仍为真（因为集合本来就已经空了），导致 `onAllReleased()` 被重复调用第二次。`ConnectionOccupancyTest.releasingTheSameTokenTwiceDoesNotFireTheCallbackAgain` 复现了这个场景；证伪记录：还原成 `activeTokens.remove(token); if (activeTokens.isEmpty())`（不看返回值）后，该测试立即打红。修复：`val actuallyRemoved = activeTokens.remove(token); if (actuallyRemoved && activeTokens.isEmpty())`。

**缺陷 2（测试假设错误，非生产代码缺陷）：** 最初给 `ShizukuFileServiceListingTest` 写的失败注入用例假设"用普通文件冒充 bundle 子目录会让 `listFiles()` 返回 null"，在真实 x86_64 AVD 上实测**不成立**——`ShizukuFileService.listBundleDirectoryPaged` 对非目录条目先 `if (!bundleDir.isDirectory) continue` 提前跳过，根本不会走到 `listFiles()`。改用 `chmod 000` 对自己进程创建的目录撤销读/执行权限，在真实设备上能真实触发 `listFiles()` 返回 null，测试改用这个注入方式后通过并可证伪。
