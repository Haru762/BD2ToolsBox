## 1. 改动概览

把有状态 Repository 的手工单例 / `get(context)` 与 ViewModel 的 `initialize(context)`+`lateinit` 装配，改成 Hilt 构造注入。

| 文件 | 改动 | 原因 |
|---|---|---|
| `di/DispatcherModule.kt` | 新增；`@IoDispatcher`/`@DefaultDispatcher` qualifier + `CoroutineDispatcher` 提供 | 统一注入 IO/Default 调度器，测试可替换 |
| `di/RuntimeModule.kt` | 新增；`fun interface Clock` + `@Singleton` 系统钟 | 提供可注入时钟 seam（不强改现有 11 处 `System.currentTimeMillis()`） |
| `di/RepositoryModule.kt` | 新增；6 个 `@Provides @Singleton`（Character/Mod/InstalledMod/BundleBackup/PreviewCache/Gamekee） | 每种仓储在应用图内恰好一个实例 |
| `ui/viewmodel/MainViewModel.kt` | `@HiltViewModel @Inject constructor(savedStateHandle, @ApplicationContext appContext, 5 仓储)`；删 `lateinit` 仓储 + `initRepositories()`；`appContext` 改注入 `val`；`initialize(context)` → `initialize()`；19 处 `::repo.isInitialized` → `true` | 构造注入替代 lateinit 装配 |
| `ui/viewmodel/GuideViewModel.kt` | `@HiltViewModel @Inject constructor(repo)`；删 `lateinit repo`；`initialize(context)` → `initialize()`；去掉 `::repo.isInitialized` 守卫 | 同上 |
| `MainActivity.kt`、`ui/screens/GuideScreen.kt` | `initialize(context)` 调用点改无参 | 配合 VM 无参 initialize |
| `app/src/test/.../di/RepositoryConstructionTest.kt` | 新增，5 条（纯 JVM，不启 Hilt） | §5 |
| 5 个 androidTest 类 | 改用「构造时传 context + 真实仓储」替代反射 set 私有字段 | 构造函数签名变化，见 §4 |

**没有改的：** `applicationId`、各 authority、组件导出、SDK 等级、权限、native/Python/打包；`ShizukuFileService`（外部进程 Binder Stub，T16 已定不接 Hilt）。

**纯静态工具不强行加 DI：** `BundleNameResolver`、`CharacterMetaRepository`、`AvatarRepository`、`UpdateRepository`、`SpineRuntimeRepository`、`Bd2RedeemRepository` 等仍保留原有 `get()`/直接构造——本任务只迁「MainViewModel/GuideViewModel 通过 lateinit+initialize 装配的那批有状态仓储」，不为形式统一波及无关调用点。

## 2. 单一事实源 / 作用域

- **账本单写不变量**：`InstalledModRepository` 的账本单写本来就由 `LedgerSubmissionCoordinator.forDir(filesDir)` 的进程级锁保证；`@Singleton` 在此之上再消除「Activity 被 MIUI 回收重建后 `initRepositories()` 各造一份、各持一份 `lastError`/缓存」的分叉。`RepositoryConstructionTest#installedModRepositoryLedgerAnchorsToInjectedFilesDir` 钉住账本文件锚定注入的 `filesDir`。
- **不把 Activity Context 放进长寿命对象**：所有仓储只依赖 `@ApplicationContext`（已核对无 Activity Context 泄漏）；`MainViewModel.appContext` 也是注入的 application context。
- **页面选择/筛选状态**不在应用级单例里：它们仍是 `MainViewModel` 的 `StateFlow` 实例状态（本任务未改其位置）。
- **重建 Activity 不新建后台任务所有者**：扫描/装入跑在进程级 `installScope` 与前台服务上（本任务未改）；仓储改单例后，重建的 VM 拿到的是同一批仓储，不会另起一套账本写入方。

## 3. `initialize` 去 context 化

`MainViewModel.initialize()` / `GuideViewModel.initialize()` 不再需要传 `context`——仓储与 `appContext` 都已构造注入，`initialize()` 只保留一次性启动装配（恢复设置/壁纸/目录、启动核对与迁移、异步初始化）并用 `initialized` 幂等守卫。调用点 `MainActivity`、`GuideScreen` 已改无参。满足验收「去掉 initialize 调用后所有入口仍可用」的实质（不再靠 context 线程化）。

## 4. 设备测试适配（构造函数签名变化）

5 个 androidTest 类原来 `MainViewModel(SavedStateHandle())` 后反射 set `appContext`/`backupRepository`。现改为构造时传入指定 context + 真实仓储（`newViewModel(ctx)` 辅助），语义不变：

- `SnapshotStoreInstanceReuseTest`：用覆盖 `getFilesDir` 的 `ContextWrapper` 构造 VM。
- `PlatformBehaviorTest`：3 处分别用 `refusingContext()` / `targetContext` 构造，删掉 `appContext` 反射 set。
- `BackupFailureSummaryTest`：`vm` 字段用 targetContext + 真实仓储构造；删掉 `appContext`/`backupRepository` 两处反射 set。
- `LedgerRecoveryStartupTest`：用 `wrapper` 构造 VM 后调 `initialize()`（原来 `initialize(wrapper)`）。
- `TryUseBackupTrustGateTest`：`vm` 用保留引用的 `backupRepo` 构造，`seedBackup` 复用它。

这些改动是**测试装配方式**的适配，不放宽任何断言。

## 9. 未覆盖（如实登记）

- **原生 arm64 运行**：B 类不要求；DI 为 dex 层，x86_64 已实跑。
- **时钟未全面接管**：`RuntimeModule.Clock` 作为 seam 提供，但现有 11 处 `System.currentTimeMillis()` 未逐一改注入（无关调用点不动，按需迁移）。
- **调度器未全面接管**：`DispatcherModule` 提供 IO/Default，但 MainViewModel 内大量 `Dispatchers.IO`/`viewModelScope` 未逐处改注入（本任务聚焦仓储/VM 装配，不为形式统一波及全部协程调用点）。
- `::repo.isInitialized` → `true` 后留下少量恒真/恒假分支（编译器 1 条 "always" 警告），行为等价、未清理死分支以缩小改动面。
