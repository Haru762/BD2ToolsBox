## 1. 为什么撤回之前的 DONE 标记

2026-09-28 的原生 arm64 测试确实是 `OK (4 tests)`，但其中解包用例只检查了非空消息，使用的是垃圾字节，没有验证有效 bundle 转换或产物。原协议测试还把越界异常当作正确结果。它们不能证明原 TODO 的全部验收条件。

本轮从已提交实现复现了四类缺陷：

1. 返回元组校验、字段转换、JSON 解析在 `callMain` 的 catch 之外；少字段或错误类型直接抛出，未形成约定失败值。
2. Kotlin 扫描异常被转成 `"[]"`；Python 的 `check_scan_needed` 也把 JSON 错误转成空名单。调用方会把失败误认为“不需要扫描”。元数据解码失败同样可能变成成功的空表。
3. `ModEngine.get()` 先构造实例，Hilt 后调用 `install()` 替换实例；早期调用方与注入方可能持有不同引擎。
4. Python 解包器的广泛 `except` 会吞掉 Kotlin 回调的 `CancellationException`。仅在 Kotlin 外层 catch 并重抛不够；加强的真设备用例实际复现了这一点。

## 2. 本轮修复边界

- **不变：** 14 个引擎方法的 Python 函数名、参数顺序、正常返回元组形状、SD/HD、ASTC、fast 和 resolver 的正常语义；无依赖升级、无 native 库替换、无 vendored 算法修改。
- **协议处理：** `ChaquopyModEngine.callMain` 覆盖调用、元组长度、字段转换与 JSON 解析全过程。两元组操作返回 `(false, diagnostic)`，元数据返回 `null`；损坏字段不能被忽略后拼成半张成功表。
- **扫描错误：** `checkScanNeeded` 抛出带函数名、CALL/PROTOCOL 阶段和原始原因的 `EngineBridgeException`。Python `check_scan_needed` 保留成功时的单元素元组，失败时保留诊断并重抛，不再返回成功空名单。这是修正已复现的协议缺陷，两端均有回归测试。
- **取消：** 直接抛出的 `CancellationException` 不吞；进度回调另在 Kotlin 侧记录取消异常，即使 Python 将它捕获，也在 native 调用返回、解码成功之前重抛。它不承诺强行中断一段无回调的 native 执行。
- **实例：** `ModEngine` 的默认实例改为不可替换的惰性实例；Hilt provider 委托同一 `get()`，删除 `install()` 与另造实例的绑定。旧访问器仍作为原计划 T20 的待清理入口，不再存在“先用旧实例、再替换新实例”的路径。
- **Python None：** Chaquopy 返回的 None 保留到字段被实际读取时再校验；合法的失败元组三项 `(False, message, None)` 不会在构造结果列表时触发空指针。

没有借本轮修复改动账本、游戏目录、Shizuku 连接生命周期或其他任务实现。
