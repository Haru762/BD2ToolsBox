## 3. 四个入口的判定规则（本项核心之一）

| 入口 | 结果来源 | 明确拒绝的情况 |
|---|---|---|
| `Test-Bd2Unit` | `app/build/test-results/<task>/TEST-*.xml` **真解析** | 无 XML；报告里没有该类；0 用例；failures/errors>0；skipped>0（`-AllowSkip` 例外）；Gradle 退出码与 XML 不一致 |
| `Test-Bd2Python` | `tools/run_python_tests.py` 的结构化 JSON | 报告缺失/不可解析；`result≠PASS`；discovered/executed=0；skipped>0；failed/errors>0；任一夹具 `ok=false`；`--required` 指定的 ID 未被发现；runner 退出码非零 |
| `Test-Bd2Device` | `am instrument -w -r` 的**逐条** `INSTRUMENTATION_STATUS_CODE`（1=开始/0=通过/-3=`@Ignore`/-4=`Assume` 不成立） | 白名单无该 ABI；同 ABI 多命中而未显式指定 serial；设备不在线；设备实报 ABI ≠ 白名单声明；`ProjectRoot` 越界；无原始协议（拒绝判定，不退回只看尾部）；`passed ≠ started`；出现 `-3`/`-4`（即被跳过，**点名**用例）；未输出 `OK (n tests)` |
| `Test-Bd2ReleaseSmoke` | apksigner 证书 + 清单哈希 + 设备内探针 + `am start -W` + `dumpsys` | case 未实现；基线 APK 缺失；哈希不符；证书不符；同上全部设备项；启动非 `Status: ok`；身份不符 |

三条贯穿性原则：

1. **退出码 0 不是验收。** 见 §6 的 F4：不存在的测试类让 `am instrument` **adb 退出码为 0**，
   而 runner 输出 `Tests run: 1, Failures: 1`——判定取 runner 终判，不取 adb 退出码。
2. **skip 不是通过。** 见 §8 的 L2：去掉夹具配置后 6 条真实兼容用例被 skip，
   `python -m unittest` 侧的退出码是 0，脚本仍判 FAIL 并列出 `skipped=6`。
   设备侧起初**没有**这道闸——`OK (n tests)` 把 `Assume` 不成立的用例也算进 `n`，
   六个 androidTest 类首轮全部报 PASS 里就藏了一条从未执行的用例（§5.3）。已补齐。
3. **未实现即非零。** 见 §6 的 F3a：未实现的 release case 一律抛错，不返回空成功。

## 4. release 契约探针：为什么另建一个自足模块

brief 原计划把 `ReleaseContractProbeTest` 放在 `app/src/androidTest/`。**实测证明这条路走不通**，
因此本项把它移进新模块 `:release-probe`（一个自足的普通应用 APK，自带完整运行时，
通过 `<instrumentation android:targetPackage="com.bd2toolsbox">` 挂到被测包上）。

两条死路各有实测记录：

| # | 做法 | 实测结果 | 根因 |
|---|---|---|---|
| 1 | debug 变体的 androidTest 包驱动 minified release 包 | `NoClassDefFoundError: Failed resolution of: Lkotlin/jvm/internal/Intrinsics;` | AGP 会把**被测 app 已提供的类**从 androidTest 包里去重，而 R8 已把它改名为 `P1.h`。DEX 解析证实：测试包里 `Intrinsics` 有 0 个类定义、2 处字符串引用；release 包里存在类定义 `LP1/h;` |
| 2 | 把 androidTest 改走 release 变体（`testBuildType=release` + `-applymapping`） | `NoSuchMethodError: No static method e(Ljava/lang/Object;Ljava/lang/String;)V in class LP1/h;` | 测试包按**当前源码**的映射混淆，而被测的是**预先构建好的**冻结基线，映射对不上 |

第 2 条另有产物级佐证：

```
$ grep -m1 '^kotlin.jvm.internal.Intrinsics ->' local/refactor-artifacts/rebuilt-original/mapping.txt
kotlin.jvm.internal.Intrinsics -> P1.h:
```

`mapping.txt:268559` 起，`P1.h` 只定义了 `a`/`b`/`c`/`d` 四个直接方法（`areEqual`、`checkNotNull`、
带消息的 `checkNotNull`、`checkNotNullExpressionValue`）；`checkNotNullParameter` **不在映射里**——
它的 `checkNotNull(Ljava/lang/String;Ljava/lang/Object;)V` 形态被 R8 合并进 `c`/`d`，
并留下 `residualsignature: (Ljava/lang/String;Ljava/lang/Object;)V`。而 T04 自身改过生产代码
（新增 `PrepackCommitPolicy.kt`、改 `PrepackService.kt`），当前源码**不可能**再生成基线那份映射。
因此「测试包与被测包同一次构建」这个前提在本项里根本不存在。

`:release-probe` 不依赖 `:app` 的任何类，故两条死路都不受影响。它**不做收缩**
（`isMinifyEnabled = false`），否则又回到「运行时被裁掉」的坑里。

`release-probe/src/main/AndroidManifest.xml` 里另有一处必要声明：

```xml
<queries><package android:name="com.bd2toolsbox" /></queries>
```

Android 11 起的包可见性：探针是**外来的 UID**，不声明就连被测包的 LAUNCHER 入口都解析不到。
只开被测包一个，不使用 `QUERY_ALL_PACKAGES`。

> 这与 plan 给 T13 安排的 `tools/compat-probe` 是同一思路：跨包契约要用自足探针证明，
> 不能用被测目标自己的测试包。

### 4.1 跑通后发现的两个潜伏缺陷（该代码此前从未被编译过）

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| 1 | 引用 `ApplicationInfo.primaryCpuAbi` | **编译不过**：`Unresolved reference: primaryCpuAbi`——它是 hidden API，compileSdk 34 的 `android.jar` 里没有 | 改用 `appInfo.nativeLibraryDir`，取末段作为载荷 ABI 目录 |

从未被编译，更没被执行过。

### 5.3.1 发现：入口把「被跳过的用例」判成了 PASS

第一轮六类**全部**报 PASS（`20260915-213325`…`-213633`），但 `ModDiscoveryTest` 的
尾部是：

```
com.bd2toolsbox.data.repository.ModDiscoveryTest:...........      <- 11 个点
Time: 3.895
OK (12 tests)
```

**11 个点、12 条用例**。原因在 `Assert-Bd2InstrumentationResult`：它只匹配尾部
`OK \((\d+) tests?\)`，而 AndroidJUnitRunner 的 `n` **把 `Assume` 不成立（code `-4`）
与 `@Ignore`（code `-3`）一并算进去**。于是被跳过的用例照样计为通过——正是本项
§3 立下的那条规则「**skip 不是通过**」在设备侧的漏网。姊妹入口 `Test-Bd2Unit` /
`Test-Bd2Python` 都显式拒绝 `skipped>0`，只有设备入口没有这道闸。

拿原始协议坐实（`am instrument -w -r`，`-r` 才会输出逐条状态块）：

```
INSTRUMENTATION_STATUS: test=realLibraryPreservesAllPreviouslyVisibleAndroidVariants
INSTRUMENTATION_STATUS_CODE: -4          <- ASSUMPTION_FAILURE

本次全部状态码分布： code 1 x12（开始）  code 0 x11（通过）  code -4 x1（跳过）
```

**被跳过的用例是 `realLibraryPreservesAllPreviouslyVisibleAndroidVariants`**，也是整个
`app/src/androidTest` 树里**唯一**一处 `Assume`：

```kotlin
val path = InstrumentationRegistry.getArguments().getString("libraryManifest")
org.junit.Assume.assumeTrue("Optional read-only directory snapshot", path != null)
```

它需要 `-e libraryManifest <path>` 指向一份捕获的只读目录快照（断言硬编码
`1044` 条 Android-only、`1741` 条混合），仓库里**没有**这个夹具，也没有任何地方传这个参数，
所以这条用例**在上机条件下永远跳过**。按 §0.3「不以预期代替结果」，它**不计为通过**——

### 7.1 M3：一个真实的覆盖竞态，原测试抓不到，已补断言

变异 `prepareDir` 不再先 `deleteRecursively()` 后，**原 9 条用例全部照常通过**。
原因不是变异无害，而是原断言只检查「某个文件不存在」：

- 解包失败路径最终由 `cache.delete(...)` 兜底清空，所以「解包失败会清掉残留」仍然通过；
- 重复预解包路径写入的是**同名**文件，覆盖后目录数仍为 1。

真正的危害在没有断言覆盖的那条路径上：**同一槽换过内容**时，上一轮的 `.atlas` 留在目录里，
而 `PreviewCacheRepository.isValid` 只要求「目录里存在**某个** skel 与**某个** atlas」——
于是「新一轮的 skel + 上一轮的 atlas」被判为**有效缓存**，用户看到两份产物拼起来的错位预览。

已补断言（`app/src/test/java/…/PrepackCacheIntegrationTest.kt`）：

```kotlin
@Test
fun `换过内容的同槽产物不把上一轮文件留在新结果里`() {
    prepack(payload = listOf("char_old.skel", "char_old.atlas"))
    assertEquals(1, cache.count())
    prepack(payload = listOf("char_new.skel", "char_new.atlas"))
    val names = slot().listFiles()?.filter { it.isFile }?.map { it.name }?.sorted().orEmpty()
    assertEquals(
        listOf(".srcsize", "char_new.atlas", "char_new.skel", "gen"), names,
        "新产物必须独占这个槽：上一轮的文件不能留下"
    )
}
```

断言的是**槽内文件名的全集**而非「存在/不存在某一个」——只有全等才能保证新产物独占该槽。
补完后重做 M3：`FAILED`，失败用例正是这一条；还原后 PASS。JVM 单测因此由 18 条变为 **19 条**，
`test-matrix.md` §3.1 已同步（9 → 10）。

### 7.2 变异实验的归档被静默覆盖：`New-Bd2RunDirectory` 的同秒撞名

处理 M2 的结果时发现归档对不上。实验当时写下的日志（本机临时目录 `mutation2.txt`，

```
      (see …\local\refactor-artifacts\test-results\20260915-164400-python-test_scan_checkpoint.py\summary.json)
```

而**今天**那个路径下的内容是：

```
summary: result PASS counts {'discovered': 5, 'executed': 5, 'passed': 5, 'failed': 0, …}
report : runId 20260915-164400-a2ed23e6 counts {… 'passed': 5 …} result PASS
```

同一个路径不可能既是 FAIL 又是 5/5 PASS —— **那份 FAIL 归档被覆盖了**。同一段日志还记了

```
   20260915-164401-python-test_scan_checkpoint.py
```

根因不在变异，而在本项自己新写的运行目录函数：时间戳只到秒，且用
`New-Item -ItemType Directory -Force` 建目录，而 `-Force` 对**已存在**的目录是**静默复用**。

两次就落到同一个目录名，后跑的 `summary.json` 把先跑的**直接盖掉**——证据没了，且没有任何报错。

对照探针（`OLD` 是修复前函数体的原样副本——它从未提交过，只在被就地改掉前的文件里存在；
`NEW` 是当前实现；两次调用用**同一个** label）：

```

[OLD] 同一目录=True   覆盖后 first.txt = SECOND
[NEW] 第一次=20260915-172445-NEW-same  第二次=20260915-172445-NEW-same-2
[NEW] 同一目录=False  覆盖后 first.txt = FIRST
```

`True` / `SECOND` 那一行就是缺陷本身：第一次写下的 `FIRST` 读回来变成 `SECOND`，
说明两次调用拿到的是同一个目录。修法（`tools/verification.ps1`）是撞名时追加序号，
**绝不写进已有目录**：

```powershell
# 时间戳只到秒：同一入口在同一秒内跑两次会**撞名**，而 New-Item -Force 会静默复用
# 目录 —— 后一次运行直接覆盖前一次的 summary.json，证据就没了。这不是假设：
# 一次变异实验的 FAIL 摘要被紧随其后的「还原后重跑」盖成了 PASS，事后只能靠
# 控制台记录才发现。因此撞名时加序号，绝不写进已有目录。
$base = Join-Path $Bd2ResultsRoot ((Get-Date -Format 'yyyyMMdd-HHmmss') + '-' + $safe)
$dir = $base
$n = 2
while (Test-Path -LiteralPath $dir) {
    $dir = $base + '-' + $n
    $n++
}
New-Item -ItemType Directory -Path $dir | Out-Null
```

这是本项对 `verification.ps1` 的**第二处功能改动**（第一处是四个入口本身）：
它不在 brief 的验收条目里，但属于「入口能不能产出可信证据」的一部分——
一个会把上一轮证据覆盖掉的入口，等于没有归档。修完后 M2/M4 重做，
FAIL 与 PASS 两份归档各自独立存在（`20260915-172035` = FAIL，`20260915-172043` = PASS），
M2 的 FAIL 从此**永久可查**（§7 的逐用例断言就是从这份归档读出来的）。

> 这条缺陷无法通过「事后补跑」完全复原：被覆盖的那份 FAIL 摘要的内容已经不存在了
> （M2 的结论是靠 `mutation2.txt` 与 §7 的重做共同支撑的，不是靠原件）。记录在此，
> 是因为一个**会吃掉自己证据**的缺陷必须在证据文件里点名，否则下一个读到
> 「四次运行只剩两个目录」的人会以为是自己数错了。

## 8. 反实验 C：设备与路径护栏

**第一次尝试是无效的，如实记录**：我最初在同一进程里改 `environment.local.json`
再调用入口，结果 G1/G3 照常跑完了 instrumentation。原因是 `$Bd2Devices` 在**点源时**
一次性读入，改文件对已加载的会话没有影响。改为**先改配置、再点源**的独立子进程后重做：

| 编号 | 配置 | 拒绝信息 |
|---|---|---|
| G1 | `deviceWhitelist` 为空 | `没有已授权设备声明 abi=x86_64。abilist 里的同名项经转译提供，不等于真实设备；该 ABI 验收保持未完成，不放宽为猜测或默认设备。` |

## 15. 记录在案的方法论偏差

1. **反实验 C 的第一轮无效**（§8）：改配置文件而不重新点源，等于没改。

   记下当时那条 FAIL 路径，这次覆盖就查不出来了。
6. **一次变异曾短暂残留在被测源码里**（`app/src/main/python/local_bundle_indexer.py`）：
   一次重做脚本在还原之前崩了，留下两处变异。更糟的是该脚本的「还原校验」是
   拿文件**自己**的 sha256 与**自己**比（`$h -eq $h`），恒为 `True`，等于没校验。
   发现它靠的是 `git diff --stat`，不是脚本自报。随后用精确 `Edit` 逐处反向改回，
   并以两道外部基准确认：`git diff` 为空，且与 `git show HEAD:<路径>` 做**行尾归一化**比对
   无差异；sha256 回到 `8E473DF0…`。
   教训：**还原校验必须对着外部基准做，不能对着自己**；`git status` 这类外部观察
   不能省略。同一个工作树还有别的会话在跑，`git checkout --` 当时被
   `index.lock` 挡住——**没有删锁**，改用 `Edit` 反向修改，避免踩到别人的操作。
7. **`$LASTEXITCODE` 会读到上一条命令的残值**（§5.1.1 末段）：在同一 PowerShell 会话里
   点源后直接调入口，再打印 `$LASTEXITCODE`，读到的是**上一条 adb 命令**的退出码——
   于是 arm64 那次拒绝显示成 `SMOKE_EXIT=0`，看起来像「拒绝了但退出码正常」。
   改成把入口放进 `ErrorActionPreference='Stop'` 的独立子进程跑、由父进程读进程退出码，
   才拿到真实的 `0`（x86_64 PASS）/ `1`（arm64 拒绝）。
   这与 §6 F4（`am instrument` 的 adb 退出码为 0）是同一类错误的两个面：
   **退出码不是验收，而读错来源的退出码连「退出码」都不是**。
8. **失败的运行根本不留归档**（§5.3.2）：`Assert` 在写 `instrumentation.txt` 之前就 `throw`，
   失败运行只剩一个**空目录**（实测 `20260915-214225-…ModDiscoveryTest`，0 个文件）。
   这与 §7.2 是同一主题的两端——那次是「归档被覆盖」，这次是「归档压根没写」。
   共同教训：**证据的落盘不能依赖后续步骤成功**，要先写现场再判定。
   附带一个查档陷阱：`summary.json` 是刻意的 UTF-8 **无 BOM**（好让 Python 侧 `json`
   正确读，见 `Write-Bd2Json` 注释），于是 Windows PowerShell 5.1 的 `Get-Content`
   按 ANSI 解码，中文 `reason` 显示成乱码——**那只是读法的问题**，按 UTF-8 读即正常。
   查归档时别被它误导成编码缺陷。
9. **「修一半」被写成了「已修」**（§5.4.1）：§5.3.2 原文写「失败也写出 `summary.json`……
   现场不丢」，但实际只覆盖了断言失败的路径，构建/安装阶段的失败照样只剩空目录。
   同一段里我自己还写着「`result = 'FAIL'` 默认值是死代码」——说明当时已经看见
   落盘挂在错误的位置，却只把结论推进到「补个 catch 就行」。**独立复核者用一次
   复现实验把它推翻**，这是本项第二次靠外部质疑纠正自述（第一次是 T03 的快照误判）。
   教训：证据文档里凡是「已修」「已覆盖」这类断言，都要问一句**覆盖的是哪条路径、
   哪条路径没覆盖**——范围没写清的成功断言，读者只能按最宽的意思理解。
10. **引文凭记忆写，产生了不可能存在的输出**（§5.4.3）：F8 那条引文
   （`必需的测试 ID 未发现`）与脚本里的字面量（`必需测试未被发现`）不一致，
   而 §14 同时登记了脚本哈希——两处放在一起就是自相矛盾：那个哈希的文件产不出那句话。
   F6 则是把两条真实 reason 揉成一句转述。**规则从本轮起：凡引用脚本产物，
   一律从实跑输出或源码字面量逐字抄，不凭记忆。**
11. **判定规则写得比实现强**（§5.4.2）：`test-matrix.md` §1 把「夹具缺失或哈希不符非零」
   列为共用规则，但只有 `Test-Bd2Python` 真的实施，`Test-Bd2Unit` 从不读 manifest。
   规则表没标「谁实施」，读者会自然以为四个入口都做。已在 §1 拆成
   「共用规则」与「夹具规则（并标明实施范围）」两张表。
   这是「文档承诺 > 实际覆盖」的一种——和 T02 那 6 条 skip 是同一类问题的不同外衣。
12. **护栏全绿是在改动之前跑的，改完没重跑**（§16）：§5.4 那两处整改动了
   `verification.ps1` 的判定路径（`finally` 落盘、JVM 夹具判定），我只补了针对新逻辑的
   定点证伪，没有把 §6–§9 的护栏整轮重放。**改了判定代码却不重放判定测试**，
   等于用「新逻辑自测通过」替换「整条链还是原来那样」。第二轮整改后补跑全量，
   结果见 §16；结论没变（八条护栏全部拒绝、`LocalAll` 仍按缺项抛错），
   但这是在写完之后才补的，如实记在这里。
