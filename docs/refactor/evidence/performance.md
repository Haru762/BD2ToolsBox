## 1. 启动与内存（设备，release）

采样规则：**冷启动 5 次**（每次先 `am force-stop`）、**暖启动 5 次**（`KEYCODE_HOME`
后拉起）、**PSS 3 次**。报告**中位数**与全部原始样本。

| 指标 | 第 1 次（登记为基线） | 第 2 次（对比） | 变化 |
|---|---|---|---|
| 冷启动中位数 | **451 ms**（445/458/439/451/452） | **448 ms**（443/441/469/449/448） | −0.7% |
| 暖启动中位数 | **59 ms**（60/59/26/68/42） | **48 ms**（28/60/48/77/40） | −18.6% |
| PSS 中位数 | **165,974 KB**（165950/166210/165974） | **157,649 KB**（157535/157789/157649） | −5.0% |

两次都在噪声内（暖启动样本本身抖动大：26–77 ms，中位数才稳）。**没有 10% 以上的回退**。

### 1.0.1 换成修复后的 release（`d70ab6a1…`）后的 12 轮复测

| 指标 | 12 轮中位数 | 轮间范围 |
|---|---|---|
| 冷启动中位数 | **426 ms** | 403 – 486 |
| 暖启动中位数 | **55 ms** | 42 – 73 |
| PSS 中位数 | **163,879 KB** | 161,663 – 167,507 |

比首版基线（451 / 59 / 165,974）**更快或持平**，所以 `MoveCommit` 的修复没有带来
性能代价。

### 1.1 基线门禁（10% 触发线 + 噪声容忍）

`Test-Bd2ReleaseSmoke -Case 'performance-scenarios'` 做两层判定：

1. **硬阈值**（与设备无关）：起不来、冷启动中位数 > 10 s、PSS 中位数 > 1.5 GB → 失败；
2. **基线对比**（与设备/API 相关）：`config/performance-baseline.json` 按 `"<abi>@<api>"`
   分键存中位数，命中且**既超过 10%、又超过容忍度** → 失败并打印原始数据路径；
   没命中就登记为基线、不做门禁（第一台设备上不该凭空失败）。

容忍度 = `max(10% × 基线中位数, 轮内全距, 轮间全距)`。

**为什么不是单纯的 10%**：这条线在本机就是噪声下限。实测两次误报：

| 现象 | 数据 | 成因 |
|---|---|---|
| 暖启动「+11.9% 回退」 | 59 → 66 ms，两次原始样本区间重叠（26..68 / 44..90） | 暖启动样本离散度本身就远超 10% |
| 冷启动「+18.8% 回退」 | 409 → 486 ms，其余 11 轮是 403..445 | **本机同时在跑 Gradle 构建** |

所以门禁用**全距**而不是 IQR：IQR 稳健，恰恰盖不住「单轮离群」——
那一轮冷启动的轮内 IQR 只有 19，照样误报。

**门禁本身也验证过会拦**：把 `x86_64@32` 的基线人为改成 `coldStartMedianMs=200`、
`pssMedianKb=100000`，同一条命令立即失败：

```
冷启动中位数 回退 128.5%（200 -> 457）
PSS 中位数 回退 57.5%（100000 -> 157547）
EXITCODE=1
```

恢复真实基线后重新通过。所以「PASS」不是「门禁没生效」。

### 1.2 本机不是受控基准环境（重要）

上面那次 +18.8% 说明：**跑这个 case 时不要并发构建**。基线里记了 `hostNote` 与
12 轮实测（冷启动轮间中位数 403..486、暖启动 42..73、PSS 161,663..167,507），
`coldStartRunMedians` / `warmStartRunMedians` / `pssRunMedians` 都留在基线里，
供以后判断「这次是不是又踩到负载」。

### 1.3 修掉的两个测量实现缺陷

1. **`Get-Content -Raw` 少了 `-Encoding UTF8`**（只在这一处漏了，脚本其余六处都有）：
   Windows PowerShell 5.1 默认按 ANSI 代码页解码，基线里的中文说明被替换成 U+FFFD，
   `ConvertFrom-Json` 直接报「无效的 JSON」。已补参数，并把基线文件的说明改成
   ASCII-only（配置文件不该埋这种坑）。
2. **PSS 采样竞态**：`pidof` 与 `dumpsys meminfo` 之间进程可能已被系统回收，
   读到的是陈旧 pid → 没有 `TOTAL PSS`。现在每次采样前重取 pid，取不到就重新拉起，
   仍读不到才报错（不让偶发竞态变成「性能回退」）。

## 2. 目录枚举次数（JVM，确定性）

性能回归里最可判定的一面：**枚举几次**。

`BundleListingSnapshotTest` 用可计数的 `File` 子类（`java.io.File` 不是 final、
`listFiles()` 可覆盖）在**真实目录树**上数实际调用次数：

| 场景 | 断言 |
|---|---|
| 6 个 bundle 的 Shared 目录 | 顶层 1 次 + 每个 bundle 1 次 = **恰好 7 次**（多了是重复枚举，少了是漏项） |
| 一个 bundle 有 3 个 hash 目录、只有第 2 个有 `__data` | 顶层 + bundle = **2 次**，命中即 `break`，不再进第 3 个 |
| 分页：`offset=0` 建快照，之后 `offset=2`/`offset=4` | 后续分页**不再枚举目录树**（调用次数不变） |

10/10 通过（含原有 7 条）。

> 踩坑记录：计数器一开始放在**实例字段**里，而 `listFiles()` 每次返回**新**实例 ——
> 于是只数到根目录那一次（期望 7、实际 1）。改成跨实例共享的计数器才对。

## 3. 转换耗时（Python，多采样）

`tools/measure_conversion.py`，`--repeat 3`，取中位数。测的是转换路径里**不需要原生库**
的两个热点：

| 阶段 | 输入规模 | 中位数 | 原始样本 |
|---|---|---|---|
| `_build_file_index`（一次 `os.walk` 建索引） | 120 个 bundle / **9,240 个文件** | **107.75 ms** | 132.59 / 107.75 / 104.59 |
| `json_to_skel`（Spine json → skel 二进制） | 60 bones / 80 slots / 6 animations | **15.23 ms** | 26.60 / 15.23 / 14.15 |

`json_to_skel` 产物 54,547 字节（非空校验）。脚本顺带断言：索引跳过 `.old` 备份目录与
`.nomedia` 标记，索引到的词干数 == bundle 数。

## 4. 明确未覆盖

- **ASTC 编解码耗时**：`libastcenc` 只在设备上有，且真机/模拟器上的实际解码仍未验
  （`docs/refactor/evidence/` 里的既有缺口）。本轮的转换耗时**不含**这一段。
- **大列表滚动帧率**：需要 UI 自动化或人工录制；未做。`BundleListingSnapshot` 的
  分页不重扫已由 §2 覆盖，但「滚动时掉不掉帧」没有数据。
- **图片峰值内存**：本仓库没有 Coil/Glide（预览走 WebView 与磁盘缓存
  `PreviewCacheRepository`），没有「图片内存缓存」这个对象可测；预览缓存的**容量上限**
  由 T24/T43 的功能用例覆盖，不是性能数字。
- **arm64 真机**：本表是 x86_64 模拟器。真机数字未采（真机当前装的是优化后 release，
  但本轮未跑性能采样）。
- **16 KB 页 / API 29 上的性能**：只跑了功能，没采性能数字。
- **网络因素**：全部场景都在本地，未区分缓存冷/热与网络耗时。
