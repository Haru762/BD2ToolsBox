## 2. 偏离：**没有引入 Coil 3**

计划把 Coil 3 写成「**可选**验证替换」，并说「暂时保留旧路径」。本轮**没有引入**，理由：

1. **与 T48–T54 直接冲突**。那六个任务的全部目标是把 APK 从 35,146,618 B 压到
   22,693,546 B（−35.4%）。Coil 3 + `coil-network-okhttp` 会带回 okhttp
   （数百 KB 量级）—— 这个 App 目前**没有任何第三方 HTTP 客户端**，只用
   `HttpURLConnection`。为图片加一个 HTTP 栈，方向与刚做完的减包相反。
2. **要修的东西不需要它**。真正的缺陷是两个**无上限**的
   `ConcurrentHashMap<String, ImageBitmap>`（`GamekeeRepository.thumbs`、
   `AvatarRepository.decoded`）加上无上限的 `battleHtmlMemory` —— 滑一遍长列表
   就把每张解码图永久留在内存里。那是内存泄漏，不是「缓存策略不够优」。
   换成按字节计预算的 LRU 共 ~130 行，无新依赖。
3. Coil 的磁盘缓存这一层**本来就已经有**（`guides/thumbs/`、`avatars/` 的原子写文件），
   计划也要求「保留现有磁盘文件缓存」。

**如果以后要引 Coil**：应该在「图片管线需要尺寸自适应、占位/失败状态统一、
取消传播」这些**现路径做不到**的事情上引，并且要连同 APK 体积增量一起评估。

### 3.1 为什么按**字节**而不是按条数

一张 256×256 缩略图约 256 KB，一张全尺寸立绘可以到 4 MB —— 差 16 倍。
按条数设上限（比如「最多 200 张」）在缩略图上刚好，在立绘上就是 800 MB。
`sizeOf` 用 `宽×高×4`（ARGB_8888）：Compose 的 `ImageBitmap` 没暴露底层分配大小，
而这个估算**偏保守**（宁可少缓存几张，也不要算小了撑爆内存）。

预算取值：缩略图 8 MB（≈32 张，够「一屏可见 + 前后各一屏」的回看）、
正文 4 MB（≈40–80 篇）、头像 8 MB。

### 3.2 `maxBytes <= 0` 表示「不缓存」

不是「无上限」—— 没有「无上限」这个选项，那正是要修的东西。
