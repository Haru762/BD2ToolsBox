> 本文写法沿 `T07.md`：**每条结论都附复算命令或原始输出**；「覆盖了」与「没覆盖」
> 分节写在明处；被推翻的预判保留原文 + 反证；证伪实验记 runId、退出码与四个计数。
>
> 本项修的是一个**已经推演出会发生**的形态（改动前代码里就能读出来，不是假想）：
> 账本一损坏，`load()` 返回空表 → 下一次 `put()` 把「只有新记录」的表**整体覆写**上去
> → 旧记录永久丢失且**没有任何日志**。写入本身还是 `File.writeText` 直接覆写目标，
> 写一半被杀就留下半截文件 —— 而下次读它又走「损坏 → 空表」这条路，闭环。

**这些数字各自决定了实现里的一处决定**：

| 探针事实 | 它决定了什么 |
|---|---|
| `parse('')` 与 `parse('null')` 都返回 `JsonNull`（合法 JSON） | 空串归 `Empty`（0 字节没有内容被判废），字面量 `null` 归 `Corrupt`（一份应该是表的文件写着 null，说明被改过） |

| `rename while held open = false` | 「持有写句柄时改名失败」是可靠的**保留原件失败**注入手段 |
| `dir.length() = 0` | 目录占位不能靠 `length()` 判，必须显式 `isDirectory`（否则会被当成空表） |

### 3.3 三份新文件的形状

**`InstalledLedgerStore`** —— 构造期**只收 `File`**（`File(filesDir, "installed_mods.json")`），
`Context` 留在仓储层。核心 API：

```kotlin
fun read(): LedgerRead                                     // 零副作用、不抛
fun save(records: Map<String, LedgerRecord>): OperationError?   // null = 成功
fun preserveCorruptFile(): File?                           // 显式、可失败
```

`LedgerRead` 五态：`NotFound` / `Empty` / `Loaded` / `Corrupt` / `IoError`。
**`NotFound` 与 `Empty` 是分开的两个 `object`**，且都放行写入 —— 这是本任务最容易被
写错的一格（见 §6 证伪 1）。`Corrupt` 与 `IoError` 都**拒绝覆写**，但处置不同：
`Corrupt` 由写入路径显式改名保留，`IoError` **不动磁盘**（内容可能完好）。

**`OperationJournalStore`** —— 同样只收 `File`。核心 API：

```kotlin
fun read(): JournalRead                                    // Absent / Loaded / Unreadable
fun append(entry: JournalEntry): OperationError?           // null = 成功
fun clear(): OperationError?
fun recoveryVerdict(ledgerRecords: Map<String, LedgerRecord>): RecoveryVerdict
```

四阶段（`JournalStage`）：`PLANNED` → `STAGED` → `TARGET_REPLACED` → `LEDGER_COMMITTED`。
`RecoveryVerdict` 三态：`Consistent` / `PendingReconciliation` / `Unknown`。

**schema 与 R8**：两个 Store 写出的都是顶层 `schemaVersion` + 单一载荷键
（`records` / `entries`），照本仓既有约定（`mod_cache.json` 是
`schemaVersion` + `indexStamp` + `entries`；`local_bundle_index.json` 是
`schemaVersion` + `scannedAt` + …）。`app/proguard-rules.pro` 新增：

```
-keep class com.bd2toolsbox.core.storage.** { *; }
```

与既有 `-keep class com.bd2toolsbox.data.model.** { *; }` **同口径**（包级规则，
新增 DTO 自动被覆盖）。**`core/storage` 整包不 import `android.*`**（复算见 §9.4）。

| **`takingARecordFromACorruptLedgerKeepsTheOriginalAndReportsItInsteadOfReturningNull`** | 销账这条路径上的损坏处置**不再静默**：原件改名保留 + `Repaired` 回传 + `consumeLastError()` 非空（三点全钉） |
| **`takingARecordFromALedgerThatCannotBeWrittenReportsTheFailureAndKeepsTheRecord`** | 销账写失败时报 `Blocked`（不是「销掉了」），且账本里那条记录**还在** |

**桩的边界（只此两处，写在用例 KDoc 里）**：`Context.filesDir` → `TemporaryFolder`；
`android.util.Log` 静态方法（**实测**它在 JVM 上抛
`RuntimeException: Method w in android.util.Log not mocked`，探针输出见 §2.2）。
其余全部走真实文件系统与真实线程。

#### 一条被删掉的判据（保留原文 + 反证）

我写过一条**概率性**原子性探针 `aWriteInFlightNeverTruncatesTheTargetToZeroBytes`：
后台线程在 20 轮大表写入期间反复采样目标，断言「从不被截断成 0 字节」。

**它的第一版（读线程读内容）在正确实现上就红了**：

```
java.lang.AssertionError: 大表写入必须成功
  expected null, but was:<OperationError(kind=IO, message=装入记录写入失败（旧账本保持原样）：
  …\.bd2staged-10877117589171562026.tmp -> …\installed_mods.json,
  detail=java.nio.file.AccessDeniedException: …
```

**根因是判据、不是实现**：宿主 Windows 上文件被打开时**不能被替换**
（探针实测：`rename while held open = false`）。改成只读 `File.length()` 后仍**偶发**
同一个异常 —— 在「三条验收命令」那次跑里又红了（`runId=20260917-232834-unit-…`，
`tests=25 failures=1`，红的正是它）。

**结论：删掉**。一条会因宿主文件句柄语义而**随机变红**的断言，无法用来主张任何事 ——
它红了不能说明实现坏了，绿了也不能说明实现对了。**换用确定性判据**：
`saveCreatesTheParentDirectoryWhenItIsMissing`（`AtomicFileWriter` 会 `mkdirs`、
`File.writeText` 不会）+ T07 自己的 `AtomicFileWriterTest`（17 条，在它自己的实现上直接测）。
**原子性的确定性证据在 T07，不在 T08** —— T08 只证明「`save()` 走的是它」。

### 7.3 计划风险回退栏的对照

计划 T08 段的风险与回退栏原文：

> **风险与回退：** 数据迁移前保留受保护原件；回退代码时不得盲目用旧账本覆盖后续已发生的游戏文件事实。

**逐句对**：

1. **「数据迁移前保留受保护原件」** ↔ 本轮的**改名保留策略**：
   `preserveCorruptFile()` 把损坏原件改名成 `installed_mods.json.corrupt-<yyyyMMdd-HHmmss>`
   再写新表 —— 原件**不删**、**不覆盖**，名字里带时间戳，用户与复核者都能按名字排序。
   **保留失败时拒绝写入**（`whenTheCorruptOriginalCannotBePreservedTheWriteIsRefused`），
   所以「原件没保住却写了新表」这个组合**不可能发生**。
   代价（会累积、本轮无清理）见 §7.2(d)。
2. **「回退代码时不得盲目用旧账本覆盖后续已发生的游戏文件事实」** ↔
   本轮的代码**本身不这么做**：`checkRecovery()` 只读、不自动补记（§7.2(c)），
   journal 不驱动任何写入。**回退时**：把 `InstalledModRepository` 恢复成
   `git show HEAD:...` 那份即可，磁盘上留下的 `install_journal.json` 与
   `*.corrupt-*` 都**不影响**旧代码（旧代码不读这两个名字的文件）。
   **但回退会丢掉「窗口核对」能力** —— 旧代码读新写的账本会失败
   （新账本有 `schemaVersion` 外壳，旧 `load()` 会当成无 `modUri` 的记录全过滤掉 →
   空表），这正是**不能用回退代替数据迁移**的地方，见 §10。

## 10. 风险与回滚

**风险（按严重度）**

1. **`recordConvertedInstalls()` 那条路径的窗口仍敞着**（§8.1）。
   产物直接装入时崩溃 → 游戏目录是 mod 版、账本没有记录、journal 也没有迹象。
   这是本轮**最大**的一格不确定性，且它是**有意保留的**（裁定 B）。
   缓解面：这条路径的写失败会上报；`removeSingleMod` 在账本没记录时会走
   「还原原版」分支（`MainViewModel.kt:2919-2925` 有对应的日志与保护），
   所以最坏结果是「用户以为没装、点卸载还原了原版」，**不会丢游戏文件**。
2. **账本 schema 变了：回退代码不再能读新账本。**
   新账本有 `{"schemaVersion":1,"records":{...}}` 外壳；旧 `load()` 用
   `TypeToken<Map<String, InstalledModRecord>>` 读顶层，会得到一条 key=`schemaVersion`
   的记录（`modUri` 为 null）→ 被旧的 `filterValues { it.modUri != null }` 过滤掉 →
   剩下 `records` 这条也因 `modUri` 为 null 被过滤 → **空表**。
   于是**回退之后用户会看到所有 mod「未安装」**，而游戏文件其实是 mod 版。
   **这正是计划风险栏「回退代码时不得盲目用旧账本覆盖后续已发生的游戏文件事实」
   所指的事**：回退可以，但**必须先备份新账本**（它就是「已发生的游戏文件事实」的记录），
   且不要在新账本在场时让旧代码跑一次写入（会把新格式覆盖成旧格式）。
3. **损坏原件会累积**（§7.2(d)）：无清理策略，本轮只登记。
4. **`ledgerResetNotice` 通道的标题写死「装入记录已重置」**（§8 第 4 条）：
   「损坏重建」与「旧格式迁移」共用它，标题看不出区别（正文文案里有）。
5. **R8 保留规则是包级的**：`-keep class com.bd2toolsbox.core.storage.**` 会保留
   该包**所有**类（含纯函数辅助），比逐个类列举保守。代价是 APK 稍大；
   收益是将来新增 DTO 不会漏。与既有 `data.model` 那条规则同一取向。

**回滚**

T08 的改动是**自包含**的：**2 个新建源码**（`InstalledLedgerStore.kt` +
`OperationJournalStore.kt`）+ **4 个新建测试**（JVM 三份 + 二轮的设备一份）+ **3 处修改**
（`InstalledModRepository.kt` / `MainViewModel.kt` / `proguard-rules.pro`）。
回滚即 `git revert` 提交。**但有一个前提动作**（风险 2）：

> ⚠️ **二轮整改（措辞 7）**：首版这里写「3 个新建源码 + 3 个新建测试 + 3 处修改」——
> 新建源码实际是 **2** 个（复核报告 §E.1 与 §3.1 line 190 的同一处错误）。
> 合计 2+3+3 = **8**，不是 9。二轮加了设备测试，现在是 2+4+3 = 9。

```
回滚前必须先把 files/installed_mods.json 备份走（它是新格式的唯一记录）
```

回滚后：`InstalledModRepository` 回到 `File.writeText` 直接覆写、
`load()` 回到「失败即空表」、journal 文件不被任何人读（`install_journal.json`
只是一个躺着的文件，旧代码不知道它的存在）。
**没有「以直接覆盖作为兼容回退」这条路** —— 那正是本任务要消灭的形态。
