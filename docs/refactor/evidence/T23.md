## 1. 本轮做了什么

### 1.1 分页不再 N 页 N 次完整枚举（核心验收项）

- 新增 `feature/mods/BundleListingSnapshot.kt`（纯 JVM，不依赖 `org.json`）：
  按路径缓存一次目录枚举结果，**`offset==0` 时重建快照**，后续页复用同一份；
  `enumerate()` 的失败语义与 T19 envelope 一致 —— 目录不存在 / `listFiles()` 返 null
  抛 `IOException`，不静默当空表。
- `ShizukuFileService.listBundleDirectoryPaged` 改为委托该快照；枚举一次、分页 N 次。
  JSON 编码留在服务层（`List<BundleEntry>` → `JSONArray`），envelope 形状与错误文案不变。

修复前后：旧实现每次取页都重建 `all`（遍历整个 `Shared/`）。1830 个 bundle、
每页 500 条时是 4 次完整枚举；现在一次列举只枚举一次。

### 1.2 游戏 bundle 索引扫描编排抽成 ScanExecutor

- 新增 `feature/mods/ScanExecutor.kt`：把原先散在 `MainViewModel` 的 check/execute
  编排收进一处，用密封结果类型区分四种检查结果（`NeedsScan` / `UpToDate` /
  `NotConnected` / `Failed`）与两种执行结果（`Finished` / `Failed`）。
  `run()` 全程自己持有一份连接占用（`GameFileAccess.acquire/release`），
  页面销毁不影响扫描；不拥有后台 scope。
- `MainViewModel`：
  - `requestGameScan` 改为 `scanExecutor.check(...)`，四种结果分别映射为用户反馈；
    删掉了原先 `ShizukuManager.isAvailable()` 的重复前置判断。
  - `confirmBundleScan` 改为 `scanExecutor.run(...)`，删掉 ViewModel 自己
    `acquireConnection/releaseConnection` 的那对调用（占用移交执行器）。
  - 构造函数新增 `scanExecutor` 注入。

### 1.3 测试接线

- 新增 `BundleListingSnapshotTest`（7）、`ScanExecutorTest`（7）。
- 3 个 JVM 接线测试 + 5 个 androidTest 构造点补齐 `scanExecutor` 参数
  （androidTest 用真实 `GameFileAccess.get()`）。
