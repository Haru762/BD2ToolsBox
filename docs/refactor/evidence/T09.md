### 2.1 唯一判定处（源码事实，改动前）

`MainViewModel.refreshBundleCleanStates()` 的循环（本工作区 `:3924-3958`）：

```kotlin
states[name] = when {
    actual == null -> BundleCleanState.ABSENT
    actual.first != expectedHash -> BundleCleanState.VERSION_MISMATCH
    actual.second < 0 -> BundleCleanState.UNKNOWN
    actual.second == expectedSize -> BundleCleanState.PRISTINE
    // 与本地备份一致也算原版：备份要么是装 mod 前从游戏目录留下的原版，
    // 要么是卸载时 restore_bundle 产出的原版。后者用 lz4 重打包，字节数与
    // 官方 catalog 会差千分之几，不认这一条的话卸载完会一直显示「被修改」。
    hasBackupRepo && actual.second ==
            backupRepository.backupSize(name, actual.first) -> BundleCleanState.PRISTINE
    else -> BundleCleanState.MODIFIED
}
```

**这是循环自证**：`backupSize` 是**我们自己**存下来的备份的字节数；备份是早先某次操作里、
**很可能正是用这同一条判据**判成「原版」之后才存下的。脏文件被洗白成原版，再拿它当
重打包基底，错上加错。

## 3. m_Hash 语义 —— 结论单独成节（裁定 B：两条路都做）

### 3.1 结论行（原文）

> **`m_Hash` 不是 `__data` 字节的 md5 或 sha256 摘要；它是 Unity Addressables 在构建期算出的
> 「内容版本号」（Hash128 / SpookyHash V2），只用作缓存路径的版本分量与去重键，不做字节校验。
> BD2 的 catalog 里真正承担内容校验语义的 `m_Crc` 字段，1966 条中有 1964 条为 0，
> 即该项目在运行时关闭了 CRC 校验 —— 所以官方 catalog 里没有任何字段能当 `__data` 的字节摘要。**

### 3.2 路线 (a)：实证对撞（亲自在真机跑）

  得到 1966 条 `{bundle 名: [m_BundleSize, m_Hash]}`。

### 3.3 路线 (b)：离线（Unity Addressables 语义）

调研产出（一手来源：Unity 官方发布包 `com.unity.addressables@1.21.18` +
`com.unity.scriptablebuildpipeline@1.21.20` 的源码）：

- `m_Hash` = `BuildResult.BundleInfos[bundle].Hash` = SBP 的 `CalculateHashVersion(item, dependencies)`，
  输入是**归档压缩之前**的序列化文件内容散列 + 依赖 bundle 名列表。
- SBP `BundleDetails` 的官方字段注释（决定性）：`Hash` 与 `Crc` 都
  **"will not change between identical asset bundles with different compression options."**
  —— **同一内容换一种压缩方式，最终 `__data` 字节完全不同，而 `m_Hash` 不变**。
  这在数学上直接排除了「`m_Hash` 是最终文件字节摘要」。
- 算法是 **Hash128 / SpookyHash V2**（2021.1+ 工程默认 `useV2Hasher=true`；旧工程可能退化为 MD5，
  但两者都对**归档前内容**算，与 `__data` 字节无关）。
- `m_Hash` 的用途：`CachedAssetBundle(BundleName, Hash128.Parse(m_Hash))` —— `name` 是缓存路径
  `BundleName` 段、`hash` 是**版本**段（`docs.unity3d.com/ScriptReference/CachedAssetBundle.html`）。
  这正解释了实测的 `Shared/<bundle>/<m_Hash>/__data` 结构，以及 739/739 的目录名匹配。

### 3.4 路线 (b) 发现、路线 (a) 采信的第二个字段：`m_Crc`

catalog 每个 bundle 条目其实有 **12 个字段**，含 `m_Crc`（Addressables 的内容校验字段）：

```json
{"m_Hash":"41cf262a…","m_Crc":3615380035,"m_BundleName":"146eeaed…",
 "m_BundleSize":87462851,"m_UseCrcForCachedBundles":true, ...}
```

**但 BD2 把校验关了**（实测）：

```
catalog bundle 条目: 1966
m_Crc==0: 1964   非0: 2
```

`crc=0` 在 UnityWebRequest / `AssetBundle.LoadFromFile` 的语义里就是「跳过校验」。
→ **`m_Crc` 不可用作通用锚点**。规划里若有人想走「自算 CRC32 去比 `m_Crc`」，此路不通。

### 3.5 结论对设计的直接影响

- **`m_Hash` 只可用于「身份/版本/路径键」**（去重、变更检测、目录名比对）—— 这是它被设计出来的用途，
  也与设备实测自洽。
- **官方 catalog 里没有任何字段能当 `__data` 的字节摘要** —— 所以「可信基准」必须**另行建立**：
  从**官方 CDN 下载**时当场采集（§5.2 实测证明 CDN 字节 == 游戏 `__data` 字节），把摘要落进 sidecar。

### 4.3 设计（`PristineVerifier.kt`）

**纯 JVM**：不 `import android.*`（§9.4 复算），只收 `File` 与可构造的数据。两个入口：

| 入口 | 输入 | 能做的判定 |
|---|---|---|
| `classify(onDisk, trusted, backup)` | 真实文件 | 有摘要基准时**逐字节**；无摘要时退到 name+size |
| `classifyListing(hashDir, size, catalog, backup)` | 目录名 + 尺寸 | **只能** name+size（游戏目录列举只有这两样） |

第二个入口的存在是 **Android 读取权限**决定的：游戏目录里的 `__data` 这个 app 读不到
（在别的应用的 `Android/data` 下，11+ 只有 Shizuku 能读），扫描层拿到的永远只是 `(目录名, 尺寸)`。

**`digester` 是构造参数、可注入**（计划硬性要求）：测试据此构造「内容不同但摘要相同」的反例，
并证明判定没有循环自证。

**流式摘要**：`StreamingDigest.sha256()` 用 64 KiB `CHUNK_BYTES` 分块（`64 * 1024 = 65536`
字节 —— 一轮曾误写成「64 KB」，二轮更正；数值影响为零），常数内存
（最大 bundle 实测 434 105 568 B ≈ 414 MB）。

**`Verdict` 枚举与 `BundleCleanState` 逐字对齐**（`PRISTINE`/`MODIFIED`/`VERSION_MISMATCH`/`ABSENT`/`UNKNOWN`），
`MainViewModel` 侧只加一个显式 `when` 映射（`:3974-3985`）。

**可信来源枚举 `BaselineSource`**（这是 T09 的核心抽象）：

| 取值 | wire 名 | 锚点 | 在 `BYTE_ANCHORED` |
|---|---|---|---|
| `CATALOG_MANIFEST` | `catalog-manifest` | 官方清单（`m_Hash` + `m_BundleSize`） | 否——**没有摘要** |
| `CATALOG_DOWNLOAD` | `catalog-download` | CDN TLS 通道 + 字节数 = `m_BundleSize` | **是** |
| `RESTORE_PRODUCT` | `restore-product` | 已锚定输入 + 确定性转换（`restore_bundle`） | **是** |
| `GAME_DIR` | `game-dir` | 采集时 name+size 对得上 | 否——锚点就是 name+size |

`BYTE_ANCHORED = {CATALOG_DOWNLOAD, RESTORE_PRODUCT}` 是「有外部锚点把具体字节钉住」的那个集合。
计划验收第 1 条「不得用待验证文件自己的摘要循环证明自己」就落在这个集合的边界上。

### 4.4 sidecar（`BundleBackupRepository.kt`，落实裁定 C）

落点 `<origin_backup>/<bundle>/<hash>/__data.game.meta.json`（与备份**同目录**，`root()` 之下）。
字段：`schemaVersion` / `sha256` / `size` / `source` / `catalogVerified` / `anchoredInputSize` /
`catalogVersion` / `quality` / `capturedAt`。

**这些是磁盘上的 JSON 键名字面量，不是 Kotlin 字段名**（二轮整改，见 §「release / R8 下的
行为与保证」）。读写两侧都用显式键（`KEY_SCHEMA_VERSION` 那组常量），
**不使用 `gson.toJson` / `gson.fromJson` 的反射字段名**。可选字段为 null 时也写出
`null` 字面量，**键集合恒等于 `META_KEYS`** —— 由
`BundleBackupRepositoryTest.theSidecarOnDiskKeySetIsExactlyTheAgreedContract` 机器检查。

- **写入时机**：`saveBackup()` 成功（备份落盘）**之后**，用 T07 的 `AtomicFileWriter` 写
  （**不**造第二份原子写）。顺序不能反——否则会留下「元数据在、备份没了」的状态。
  （一轮 §4.4 曾写「那种状态骗得过 `trustedBaseline()`」；复核者实测**该声称不成立**
  —— `trustedBaseline` 先要求 `backup.isFile && length() > 0`，孤儿 sidecar 拿不到基准。
  故二轮改口径为：**顺序上的冗余保险，不是必要前提**。）
- **已有备份不覆盖、也不补写 sidecar**：补写等于替一份来源不明的旧字节凭空声明来源。
- **`catalogVerified` 由 `deriveCatalogVerified()` 逐来源推导**（`internal`，可单测）：
  - `CATALOG_DOWNLOAD` / `GAME_DIR`：`catalogSize == 备份产物字节数`
  - `RESTORE_PRODUCT`：`anchoredInputSize == catalogSize`（产物是 lz4 重打包，**永远**对不上官方字节数）
  - `CATALOG_MANIFEST`：恒 false（它不是备份的来源）
  - `catalogSize == null`（离线无缓存）：恒 false
- **旧备份（无 sidecar）**：`trustedBaseline()` 返回 null → 判定落 UNKNOWN，**不回退到「大小相等即可信」**。

## 5. 删掉「备份大小即原版」判据 —— 单独成节（裁定 A）

### 5.1 删了什么

`MainViewModel.refreshBundleCleanStates()` 里这两行（改动前，本工作区 `:3939-3941` 一带）：

```kotlin
hasBackupRepo && actual.second ==
        backupRepository.backupSize(name, actual.first) -> BundleCleanState.PRISTINE
```

连同它的注释一起删除。替换为 `verifier.classifyListing(...)` + `byteAnchoredBaseline(...)`。

### 5.2 替代判据是什么

**卸载/还原后状态能回到 PRISTINE，靠的是一条「派生锚定」链**，而不是「尺寸相等」：

1. 卸载时基底来自 **CDN 下载** → 输入是官方 `.bundle`。**实测证明它的字节与游戏缓存
   `__data` 逐字节相同**（§3.2 的 5 条对撞），且字节数 = catalog `m_BundleSize` → **输入被外部锚定**。
2. `restore_bundle` 是**确定性**转换（UnityPy 载入 + lz4 原样保存）。**实测两次运行字节完全相同**
   （见下）。
3. 产物存成备份时，`provenance.source = RESTORE_PRODUCT`、`anchoredInputSize = base.length()`
   （输入大小 = 官方值）→ `deriveCatalogVerified` 推得 `true` → sidecar 记下**产物自己的 sha256**。
4. 之后干净检测遇到这个 bundle：游戏目录里的字节就是这份产物，`byteAnchoredBaseline` 交出基准，
   `classifyListing` 第 4 条（目录名 + 尺寸对得上可信备份）→ **PRISTINE**。

**产物与官方差千分之几这件事是实测的**（宿主 UnityPy，模拟 `restore_bundle` 算法；
**版本号存疑** —— 复核者指出 1.25.3 下复现不出、只有 vendored 1.23.0 能跑，见 §9.3）：

```
CDN src      : 1168  3abc95ac18cd21242be76990…
restore #1   : 1162  1241be5abb0564c53b21a5c3…
restore #2   : 1162  1241be5abb0564c53b21a5c3…
两次一致(确定性): True
产物 == CDN源  : False        ← 差 6 字节（约 5‰），旧判据存在的全部原因
```

所以 `RESTORE_PRODUCT` **不能**用「产物字节数 == catalog」当锚点（永远不等），
必须用「**输入**大小 == catalog」。这就是 `anchoredInputSize` 字段的来由。

> **二轮补充（复核者 §4.9 的发现）**：**产物与 CDN 源不是同一串字节**（1168 → 1162，差 6 字节）。
> 因此扫描层第 4 条认它 PRISTINE，是**接受了一个 6 字节偏差的「近似原版」** ——
> **不是字节级原版**。这个偏差来自 `restore_bundle` 的重编码（UnityPy 载入 + lz4 重新保存），
> 是**确定性**的（同输入两次字节完全相同），所以它可复现、可锚定；但「卸载后回到的是原版的
> **等价物**，不是原版本身」这个含义必须写在这里，不能让人以为它是逐字节还原。
> **行为不改**（引入「产物 vs 原版」的容差语义是 Design 决定，非 T09 范围）。

### 5.3 卸载场景的实测结果

- **确定性**：`restore_bundle` 同输入两次产出字节完全相同（上）→ 派生链成立。
- **CDN 字节 == 游戏 `__data` 字节**：5/5 命中（§3.2）→ 输入锚点是真的。
- **扫描层用例**（`PristineVerifierTest.listingAcceptsByteAnchoredRestoreProductEvenThoughSizeDiffersFromCatalog`）：
  catalog 官方 1168、备份产物 1162（差 6 字节）、`source = RESTORE_PRODUCT` →
  断言 **PRISTINE**。绿色。
- **对照用例**（`listingWithoutTrustedBackupFallsBackToModifiedForRepackedBytes`）：
  同场景但**没有**可信备份 → 断言 **MODIFIED**（不是 PRISTINE）。

### 5.4 行为变化与代价（如实登记）

**旧备份从此不再被信任**：T09 之前存下的 `__data.game` 没有 sidecar → 拿不到基准 →
`classifyListing` 落 UNKNOWN。后果：

- 卸载这些 bundle 时 `tryUseBackup` 拒绝本地备份 → 改走游戏目录或 CDN 下载 → **要重新下载一次**。
- 状态显示：这些 bundle 若游戏目录字节与 catalog 不符，会显示「被修改」（MODIFIED），不是 PRISTINE。

**换来的**：来源不明的字节不会被当原版用。这是**有意的取舍**，写在此处供复核。

### 6.5 release / R8 下的行为与保证（二轮新增）

一轮对 release/R8 **零字提及**，而 T09 的 sidecar 恰是**唯一的持久化格式**，
在 release 下曾**完全失效**（真缺陷 1）。这一节把这条链在 release 包里的保证写清，
并如实标出**没能验的**。

#### 6.5.1 失效机制（一轮交付态，实测铁证）

一轮的 sidecar 用 `gson.toJson(BackupMeta)` 写、`obj.get("schemaVersion")` 读，
KDoc 声称「`-keep class com.bd2toolsbox.core.storage.**` 保护了字段名」。
**那条规则护不到 `BackupMeta`** —— 它是 `private` 类，位于
`com.bd2toolsbox.data.repository`，不在 `core.storage` 包内。

本机 R8 产物静态证据（`./gradlew :app:minifyReleaseWithR8`，产物在
`app/build/outputs/mapping/release/` 与 `app/build/intermediates/dex/release/minifyReleaseWithR8/`）：

```
# mapping.txt:201072 —— 类名与字段名全被改写
com.bd2toolsbox.data.repository.BundleBackupRepository$BackupMeta -> n1.t:
    int schemaVersion -> a
    java.lang.String sha256 -> b
    long size -> c
    java.lang.String source -> d
    boolean catalogVerified -> e
    java.lang.Long anchoredInputSize -> f
    java.lang.String catalogVersion -> g
    java.lang.String quality -> h
    long capturedAt -> i

# configuration.txt 里搜 BundleBackupRepository：零命中（没有任何规则兜住它）
# dexdump 的 Ln1/t; 实例字段名实测为 'a'..'h'
```

失效链（两处一起看才成立）：**写侧** Gson 反射取字段名 → 写出 `{"a":…,"b":…}`；
**读侧** 用字面量 `obj.get("schemaVersion")` → **恒 null** → `readMeta` 恒返回 null →
`trustedBaseline()` / `byteAnchoredBaseline()` 恒 null → 扫描层全落 UNKNOWN、
`tryUseBackup` 恒拒绝本地备份。**debug 下完全看不出来**（debug 不跑 R8）。

#### 6.5.2 二轮的保证（**不依赖反射字段名**）

**修法：读写两侧都用显式 JSON 键**（`BundleBackupRepository` 的 `KEY_SCHEMA_VERSION`
那组常量），**不使用 `gson.toJson` / `gson.fromJson`**。选它而不是「加 keep 规则 /
加 `@SerializedName` / 挪包」的理由写在 `BundleBackupRepository` 的常量注释里，要点是
**另外三种都依赖「记得回来加规则 / 别挪出去 / `-keepattributes` 配全」这个易忘前提**，
而 T09 首版正是栽在这上面。

**这条保证如何被验证（本机 R8 产物，实测）**：用二轮交付态重跑
`./gradlew :app:minifyReleaseWithR8`，再 `dexdump` 反汇编 release dex：

```
# 1) 字段名照样被 R8 改写（证明改名这件事仍然发生，修的不是「让它别改名」）
mapping.txt: com.bd2toolsbox.data.repository.BundleBackupRepository$BackupMeta -> n1.t:
    int schemaVersion -> a ; ... ; long capturedAt -> i
dex 里该类实例字段名 = 'a'..'h'      ← 与一轮一致

# 2) 但我们那组键名字面量在 release dex 里**全都在**（它们现在是代码里的常量，不是字段名）
$ dexdump -d .../classes.dex | grep '"<key>"'
  "schemaVersion": 9 处   "catalogVerified": 3 处   "anchoredInputSize": 3 处
  "sha256": 4 处          "catalogVersion": 3 处    "capturedAt": 3 处
  "size": 6 处            "quality": 9 处           "source": 9 处
```

→ **字段名被改成什么、类被挪到哪个包、`-keep` 规则有没有，都不再影响磁盘格式**：
写侧 `addProperty("sha256", …)` 用的是编译期常量，读侧 `obj.get("sha256")` 用的是同一个
常量，与 `BackupMeta.sha256` 这个**字段名**完全解耦。

**机器检查（不只靠这段声明）**：
`BundleBackupRepositoryTest` 的三条 JVM 用例把它变成可执行的合约 ——

- `theSidecarOnDiskKeySetIsExactlyTheAgreedContract`：写出的 JSON **键集合恰好**是约定的
  九个字面量（既对 `META_KEYS`，也对硬编码字面量集合）。
- `theSidecarKeepsEveryKeyEvenWhenOptionalValuesAreNull`：可选值全 null 时键集合不缩水
  （Gson 默认会省略 null 字段，那会让读侧 `?: return null` 静默失效）。
- `aSidecarWrittenWithRenamedKeysYieldsNoBaseline`：**把 sidecar 换成 R8 改名后的短键名
  （`a`/`b`/`c`…）必须读不回来** —— 这是失效形态的直接证伪对象。

`app/proguard-rules.pro` 的注释也同步改对（原文「包级规则自动覆盖新增 DTO」正是这次
失效的根因，已改成「只覆盖 `core.storage` 包 + 持久化格式不许依赖反射字段名」）。

## 10. 风险、回滚与编排者裁决点

### 10.1 行为变化（用户可见）

**旧备份不再被信任**（§5.4）。回滚代码即可回到旧行为，但**不能**盲目回滚——旧判据是循环自证，
回滚等于把「来源不明的字节可被当原版」放回来。若确需回滚，最小面是：把
`refreshBundleCleanStates` 里的 `byteAnchoredBaseline` 换回 `backupSize`（其余不动）。

### 10.2 已知风险

1. **`classifyListing` 第 4 条仍只比尺寸**。扫描层没有字节可读，这是上限。区别在**比的是谁**：
   旧=任意备份的原始大小；新=只与 `BYTE_ANCHORED` 来源（CDN 下载 / 由它派生）+ 采集时过 catalog
   校验的备份比。残余风险（一个恰好同尺寸的 mod 会被放过）由使用点的字节级 `classify` 兜住。
2. **`currentCatalogVersion` 从缓存文件名反推**。若磁盘上没有 `catalog_{画质}_{版本}.json`
   （首次运行、刚清过缓存）会返回 null —— 但该字段**不参与判定**，只做追溯。
3. **`restore_bundle` 真机未验**（§9.3）。

### 10.3 需要编排者裁决 / 我未能核实的点

- **T10 的验收命令仍有未决问题**（裁定 D 的理由）。我按计划顺序先做 T09，未动 T10。
- **`restore_bundle` 在真机 Chaquopy 下的确定性**：宿主实测成立，真机未验。若编排者要闭合，
  需要一次设备侧「CDN 下载 → restore_bundle → 两次产物比对」。
- **`m_Crc` 若将来被 BD2 打开**（1964/1966 为 0，仅 2 条非 0）：那时它可成为一个真正的字节级锚点，

3. **`MainViewModel` 三个调用点在 JVM 层的可测性**：本轮**收窄了一格** ——

   `tryUseLocalBundle` 两处仍只有编译 + 人工核对（§9.3）。

**已知盲区（保留并写准，不许当「已覆盖」读）**：「没有全量读进内存」**断言证明不了**
