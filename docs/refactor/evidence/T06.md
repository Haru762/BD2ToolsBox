| `'nested/../../evil'` | `nested_.._.._evil` | `<tmp>\output\nested_.._.._evil.png` | **否** |
| `'a/../../b'` | `a_.._.._b` | `<tmp>\output\a_.._.._b.png` | **否** |

```

'..\..\evil'（只有 Windows 语义才逃） dest=<tmp>\probe_31\..\..\evil.png  inside=False  写盘=成功
```

**结论（诚实版）：`'/'` 早在改动前就被 `replace('/', '_')` 消掉了，所以 `'../../evil'`
这一类在 POSIX（生产 Android）与 Windows 上都逃不出去。Python 这半边的加固是
「让两端行为一致」的纵深防御，不是一次已证实的生产越界。** 计划把它当成一个漏洞来修，
实测把这个说法**推翻了一半**（Windows 语义下确实逃、生产平台上逃不了），本文按实测登记。

### 2.3 另一条**真的属于 POSIX** 的 Python 缺陷：NUL

同一份探针的第 3 段：

```
base_name='a\x00b' -> dest='/data/out/a\x00b.png'
   写盘: ValueError: embedded null character
base_name='\x00'   -> dest='/data/out/\x00.png'
   写盘: ValueError: embedded null character
```

NUL 在任何平台上都会让 `open()` 抛 `ValueError`，一次抛就把**该资产的导出**整个打断。
这不是纵深防御，是两端都成立、真实可达的缺陷 —— 所以 `_safe_export_name` 里的
`replace('\x00', '_')` 是本次**确有修复价值**的一项，与反斜杠那一项性质不同。

### 2.4 三条「不能靠常识、必须实测」的事实（全部复算过）

| 说法 | 实测结论 | 出处 |
|---|---|---|
| 「同前缀兄弟目录用字符串前缀判不出来」 | 裸字符串 `'output-evil\x.txt'.startsWith('output')` = **true**（误判为在内）；`Path.normalize().startsWith(rootPath)` = **false**；canonical+分隔符判定 = false | `t06-kotlin-before-out.txt` 末段 |
| 「`File.getCanonicalFile()` 能挡 junction」 | **挡不住**。`link\x.txt` 的 `getCanonicalPath()` 原样返回 `…\output\link\x.txt`（**不解析**）；`toRealPath()` 解析成 `…\outside\already.txt`。只靠 canonical 的实现在宿主测试里会**假绿** | 同上 junction 段 |
| 「`toRealPath()` 能直接用在待写入路径上」 | **不能**。`link\x.txt`（叶子还不存在）`toRealPath()` 抛 `NoSuchFileException` —— 所以只能对「最近的存在祖先」取 `toRealPath()`，再把不存在的尾巴字面拼回去 | 同上「nearest-existing-ancestor walk」段 |

第三条的实测形状正是实现里 `realPathOf` 的写法：

```
deep                                 = …\output\link\no\such\deep.txt
nearest existing ancestor (NOFOLLOW) = …\output\link
its toRealPath()                     = …\outside
rebuilt real path                    = …\outside\no\such\deep.txt
startsWith(root real path)?          false   <-- 必须为 false 才抓得住 junction 逃逸
```

另有一条**顺带测出来、与安全无关但影响异常类型契约**的事实：Windows 拒绝以空格结尾
的路径元素，`Path.normalize()` / `toRealPath()` 直接抛
`java.nio.file.InvalidPathException`（它**本身**就是 `IllegalArgumentException` 的子类）。
原始输出 `local/scratch/t06-name-out.txt`。实现里因此把这条例外包了一层中文原因，
**不改变契约要求的异常类型**。

**这条跳过的代价必须说清（改后补记，2026-09-17 独立复核点出）**：跳过不安全条目

1. POSIX 上 `/` 是唯一分隔符，而拍平已经把最后一个 `/` 之前**全部丢掉** —— `..` 无法作为
   路径段存活，这是表达式本身的性质，不依赖任何加固。
2. 唯一「逃逸」的裸 `..` 指向父目录本身，写入被拒（不会产生文件）；且入口 3 的
   `destDir` 是**预览用临时目录**，入口 2 的 `destDir` 同样是 temp。
3. 两处的调用方**各自**有 `try/catch(/finally)`：入口 2 在 `initiateMerge`（`:2701`）
   的 `viewModelScope.launch` 里，失败置 `MergeState.Failed`、`finally` 删 `tempDir`
   （`:2711-2745`）；入口 3 在 `prepareAndShowPreview`（`:4163`）的 `launch` 里，
   失败置 `PreviewState.Failed`、删 `tempDir`（`:4168-4205`）。
   **两处都不在 `processSingleJob` 里** —— 初版写成「都在 `processSingleJob` 的
   catch 里」是事实错误（2026-09-17 独立复核指出并已按行号更正）。
   失败路径的**形状**（转成 Failed 状态 + 清临时目录）与入口 1 同构，结论方向不变。

**未覆盖的诚实部分**：入口 2/3 在**宿主 Windows 上确实能逃**（上表 3/13）。我没有改它们，
理由是本任务的生产平台是 Android(POSIX)、这两处落在临时目录、且改它们会触碰

## 10. 风险与回滚

**风险（按严重度）**

1. **误拒真实 MOD 条目**（最大风险）：§3.4 那两条拒绝规则（任何 `..` 段、任何 `\`）
   在真实归档上的误拒率**没有数据**（仓内零个 `.zip`，§7.2(d)）。缓解面：

   留 `Log.w`、在 `MainViewModel` 侧转成 `JobStatus.Failed`。**上线前值得拿几个真实
   MOD 归档数一遍有多少条目会命中这两条** —— 这是我没有数据、也不该假装有的一格。

   若将来 Windows 变成可达平台，这两处需要补。
3. **符号链接覆盖不完整**（§7.2(c)）：junction ≠ symlink，文件型 symlink 未覆盖。

无 ABI 变更。回滚即 `git revert` 提交（或反过来丢掉这四处 diff），不需要数据迁移。
`entryNameRejectionReason` 是**纯函数**，入口 4 的过滤去掉后行为回到改动前，
