## 3. 前台服务与通知

实测事实（API 34 logcat，`local/t15/device-api34/logcat.txt`）：instrumentation 进程回桌面后仍是 `uidState: FGS`，`Background started FGS: Allowed`。**被 instrument 的进程在同进程测试里构造不出系统拒绝**，所以「被拒」用例在 `Context.startForegroundService` 上注入系统的真实异常类型（API 31+ `ForegroundServiceStartNotAllowedException`，更早 `IllegalStateException`），驱动的是生产的 `start()` 与 `processInstallJobs`。「前台允许启动」一侧是真启动，断言 `dumpsys` 里 `isForeground=true`。

| 行为 | 结果 |
|---|---|
| 前台启动 InstallService | 四台设备都进入前台状态，stop 后离开 |
| 被拒时 `start()` | Install / Scan / Prepack 三者都返回 false，无前台残留；同进程真实 Context 对照返回 true |
| 被拒时装入批次 | 两个 job 都成为 `Failed("系统不允许在后台启动任务，请回到应用界面后重试")`，明细含「目标未改动」；汇总 `failedJobs=2, successfulJobs=0` |
| 通知被拒（API 33+，`revokePostNotificationPermissionWithoutKillForTest`） | 前台服务照常进入前台；进度通知不可见。API 29：无此运行时权限，通知默认可用 |
| 前台服务类型 | 三个服务都是 `dataSync`、不导出 |
| dataSync 超时 | targetSdk 34 **不适用**（6 小时上限只对 targetSdk 35+ 生效），未实现 `onTimeout`；升 target 时必须补 |

`pm revoke POST_NOTIFICATIONS` 与改 `REQUEST_INSTALL_PACKAGES` appop 都会让系统杀掉 app 进程（实测 `Killing …: REQUEST_INSTALL_PACKAGES changed`），测试与 app 同进程，所以前者改用不杀进程的 TestApi，后者不在测试里切换（§4）。

## 5. 16 KB 页

### 5.1 修复前（T14 的 x86_64 release，API 36 16 KB AVD）

- 链接对齐（静态，`local/t15/so-align-static.txt`）：arm64 93 个 .so 中 11 个、x86_64 81 个中 13 个只有 4 KB PT_LOAD 对齐。APK `lib/` 下两份自带 JNI（`libastcenc.so`、`libtexture2ddecoder.so`）是 4 KB；其余在 Chaquopy wheel（`.imy`）里：PIL `_imaging*`、`libfreetype`、lz4 三个扩展，x86_64 另有 `_brotli`、`libjpeg_chaquopy`。
- ZIP 对齐：`lib/` 下全部 STORED、数据偏移 16 KB 对齐（从 T03 起即如此）。
- 设备：Android 16 自动进入页大小兼容模式（`pageSizeCompat=4`），**每次冷启动弹系统对话框「This app isn't 16 KB compatible. ELF alignment check failed…」**（`AppWarnings: Showing PageSizeMismatchDialog`）。兼容模式下 Runtime/Dependency probe 全过。

### 5.2 修复

1. `libtexture2ddecoder.so` 按 [native-texture-decoder.md](../native-texture-decoder.md) 的固定源码 + NDK 26.3 重编，加 `-Wl,-z,max-page-size=16384`。两 ABI 每个 PT_LOAD `p_align=0x4000`，20 个必需导出齐全，依赖只有 libc/libm/libdl；连续两次构建逐字节相同：x86_64 `50e695b811e5ada33ceef564df0c4a174711cd718454f8309d115835125231c9`（563768 B），arm64 `cd75798a50a6750c1292202c3f3c42341ea751574c5e6a85eaed4ff6f3dd6e91`（603056 B）。导出集合与旧库相同；去地址反汇编 x86_64 逐条相同，arm64 仅 2 条 `ldr` 页内偏移写法随布局变化。旧库保存在 `local/t15/jnilibs-before/`。
2. `libastcenc.so` 来源未知（T12 已接受的 UNKNOWN），无法重编；wheel 内的库属于 Chaquopy 依赖包。因此 manifest 声明 `android:pageSizeCompat="enabled"`：安装时直接以兼容模式安装，不再弹系统警告（全新安装后 `dumpsys package` 报 `pageSizeCompat=32`，即 MANIFEST_OVERRIDE_ENABLED；覆盖安装旧版时报 36，多出来的是系统自带兼容标记 0x4。API 35 及以下忽略该属性）。

### 5.3 修复后

| 检查 | 结果 |
|---|---|
| release APK `lib/` 链接对齐（`local/t15/align_check.py`） | 两 ABI 各 11 个库：10 个 `0x4000`，只剩 `libastcenc.so` 为 `0x1000` |
| release APK ZIP 对齐 | 全部 STORED、偏移 % 16384 = 0 |
| 静态审计 `audit_native_abi.py` | 两 ABI PASS，failures 0；warnings 从 3 项降到 2 项（`libtexture2ddecoder` 的 4 KB 警告消失，剩 `libastcenc` 与 T49 的双 ABI bootstrap） |
| API 36 16 KB AVD 冷启动 | 不再出现 PageSizeMismatchDialog（logcat 计数 0），直接进入引导页 |
| API 36 16 KB AVD release probe | Runtime `OK (1 test)`、failures=0；Dependency `OK (2 tests)`；Fatal/SIGSEGV/SIGABRT/FORTIFY/tombstone 0 |
| **反证：同一源码改成 `pageSizeCompat="disabled"`** | 同一 AVD 上 Runtime/Dependency 都 FAIL：`lz4`、`brotli`、`UnityPy`、`main_script` 导入失败，`dlopen failed: … program alignment (4096) cannot be smaller than system page size (16384)`（`_brotli.so`、lz4 `_version.so`、`libjpeg_chaquopy.so`）。**兼容模式是当前能在 16 KB 设备上运行的必要条件**，不是装饰 |

`PlatformBehaviorTest#packagedJniLibrariesAre16KbAligned` 分别检查链接对齐与 ZIP 对齐，`libastcenc.so` 作为登记例外必须**仍是** 4 KB（换成 16 KB 版本时会红，提醒改成 `pageSizeCompat="disabled"`）。`jniLibrariesLoadOnThisPageSize` 在四台设备上真实 `System.loadLibrary` 两个自带 JNI。

**仍需后续处理（移交 T49/T51）：** 换 16 KB 对齐的 astcenc（需要可追溯源码）与 Chaquopy wheel（需上游或自建 Pillow/lz4/brotli/freetype/jpeg），之后把 manifest 改成 `disabled`，让任何 4 KB 回归直接失败。没有用 strip 或压缩代替修复。

## 8. arm64

按 [arm64-verification-policy.md](../arm64-verification-policy.md)，T15 是 B 类任务。但本任务替换了 arm64 的 `libtexture2ddecoder.so`，属于「修改 native」，按策略 §C **升格为 A 类**。

- 静态审计：`app-arm64-v8a-release.apk` **PASS**（failures 0，20 个 decoder 导出齐全，e_machine 183，16 KB 对齐见 §5.3）。
- **未在原生 arm64 运行。** 本次没有连接 arm64 真机。新 arm64 库与旧库的导出集合相同，去地址反汇编只差 2 条 `ldr` 寻址写法，由同一 NDK、同一源码、同一命令（仅多一个链接旗标）产生；x86_64 同配方库已在三台设备上 dlopen 与 BC1 解码通过。这些是推断依据，不能替代 A 类要求的原生运行。
- 需要补：在原生 arm64 真机（隔离包名，同 T14 §6.2 的做法）上跑 `ReleasePythonRuntimeProbeTest`（含 BC1 精确输出）与 `ReleasePythonDependencyProbeTest`。可以与 T18/T49 的下一次真机连接合并。
