## 2026-10-13 补：设备上真实的 ASTC 编解码往返

长期缺口是「ASTC 实际解码未验」—— 此前只验到 `System.loadLibrary("astcenc")` 能加载
（`PlatformBehaviorTest`），没有真的压过一张图再解回来。

新增 `app/src/androidTest/.../core/engine/AstcRoundTripTest.kt`（3 条），走生产
`repacker.compress_image_astc` 与 `texture2ddecoder.decode_astc`：

| 用例 | 断言 |
|---|---|
| `astcEncodeDecodeRoundTripPreservesFlatRegions` | 64×48 RGBA（三块纯色 + 一块伪随机噪声）编码 → 解码 → 逐像素比对 |
| `astcBlockSizeIsHonoured` | 4×4 与 8×8 的块数公式：`ceil(w/bx)*ceil(h/by)*16`，且 8×8 恰为 4×4 的四分之一 |
| `astcRejectsAnImageTooSmallForOneBlock` | 2×2 图（比一个块还小）：要么补零编成 1 个块，要么**明确报错**；不允许静默产出 0 字节 |

### 实测（MuMu x86_64 / API 32）

```
Device 127.0.0.1:16384 [com.bd2toolsbox.core.engine.AstcRoundTripTest]: 3 tests -> PASS
```

往返数字（原始结果字符串）：

```
encoded=3072 expect=3072 mae=4.820 maxdiff=121 noisy_mae=25.706 noisy_max=?
flat_maxdiff=0 flat_ok=True
```

- **块布局正确**：`encoded == expect == ceil(64/4)*ceil(48/4)*16 = 16*12*16 = 3072`；
- **平坦区完全无损**（`flat_maxdiff=0`）—— 这一条最能说明问题：布局错位或通道顺序
  （RGBA/BGRA）弄反都会在这里露出来，而只看平均误差时它们可能被平滑掉；
- **噪声区确实有损**（`noisy_mae=25.7 > 0`）—— 证明真的过了压缩，不是直通；
- 整图 `mae=4.82`。

### 测试里踩到的两个坑

1. **`import repacker` 拿到的是包**，模块是 `repacker.repacker`；且 `repacker.repacker`
   依赖 `UnityPy`，必须先 `import unpacker`（它负责把 vendored 目录插进 `sys.path`），
   否则得到 `ModuleNotFoundError: No module named 'UnityPy'`。生产路径本来也是
   先经过 unpacker 才用到 repacker，所以这不是绕过什么。
2. **全图 `maxdiff` 不是有意义的画质门禁**：ASTC 4×4 对伪随机噪声是最坏情况，
   实测 `maxdiff=121` 全部来自噪声区。已改成「只在平坦区判 maxdiff == 0」，
   噪声区只给一个宽松上界（防止编码器完全没在干活）。
   另外 Python 打的是 `True`/`False`，拿它和小写 `"true"` 比会把成功的用例判成失败。

### 补：ASTC 编解码耗时（T59）

`astcEncodeAndDecodeTimingIsReported`（同一类，第 4 条）在设备上量 512×512（4×4 块）：

| 阶段 | 中位数 | 原始样本 |
|---|---|---|
| 编码 | **86.9 ms** | 101.3 / 86.1 / 86.9 |
| 解码 | **9.5 ms** | 10.5 / 9.5 / 9.5 |

产物 262,144 字节（= 128×128 块 × 16 字节）。输入是带梯度的内容而不是纯色 ——
纯色会让编码器走捷径，测出来偏快。

判据只给一个很松的上界（30 s）：耗时的绝对值随设备差几个数量级，拿一个具体数字
当门禁只会变成假失败。要钉住的是「它没退化成纯 Python 实现」。

> 第一版把产物字节数那个变量叫 `blocks`，名字有误导（断言本身是对的）。
> 已改名 `encoded_bytes` 并加注说明。
