## 1. 改动概览

引入 Hilt 依赖注入的**基础设施**（Application + 各入口），不做任何依赖的构造注入迁移——那属于 T17。因此本任务：无 `@Inject` 字段、无 `@Module`/`@Provides`、无自定义 `@EntryPoint`，只建立对象图与受支持入口。

| 文件 | 改动 | 原因 |
|---|---|---|
| `gradle/libs.versions.toml` | 新增 versions `ksp=2.2.20-2.0.3`、`hilt=2.58`、`androidxHilt=1.3.0`；libraries `hilt-android`、`hilt-compiler`、`androidx-hilt-lifecycle-viewmodel-compose`；plugins `ksp`、`hilt` | T13 已验证组合 |
| `build.gradle.kts`（根） | 声明 `ksp`、`hilt` 插件（`apply false`） | 插件版本只在根脚本声明 |
| `app/build.gradle.kts` | 应用 `ksp`、`hilt` 插件；依赖 `implementation(hilt.android)` + `ksp(hilt.compiler)` + `implementation(androidx.hilt.lifecycle.viewmodel.compose)` | compiler 走 KSP，无 kapt |
| `app/src/main/java/com/bd2toolsbox/Bd2Application.kt` | 新增 `@HiltAndroidApp class Bd2Application : Application()` | Hilt 应用入口 |
| `AndroidManifest.xml` | `<application android:name=".Bd2Application">` | 注册 Application |
| `MainActivity.kt`、`SpinePreviewActivity.kt` | 加 `@AndroidEntryPoint` | 两个界面入口 |
| `service/InstallService.kt`、`ScanService.kt`、`PrepackService.kt` | 加 `@AndroidEntryPoint` | 三个**本进程**前台服务 |
| `app/src/androidTest/.../di/HiltEntryPointTest.kt` | 新增，4 条 | §5 |

**没有改的：** `applicationId`、FileProvider / Shizuku provider authority、组件导出属性、minSdk/targetSdk、任何权限、任何 native/Python/打包。

**`ShizukuFileService` 刻意不接 Hilt：** 它是跑在外部 shell 进程（Shizuku UID）里的 Binder Stub，`@AndroidEntryPoint` 会让它依赖主进程的 `SingletonComponent`，而那个对象图在 shell 进程里根本不存在。已在 `Bd2Application` 的类注释里写明这条边界。实测确认它没有被加 `@AndroidEntryPoint`，KSP 也没为它生成注入基类（§3）。

## 2. Application 不抢先启动 Python / 不阻塞首屏

`Bd2Application` 只做 `@HiltAndroidApp` 的对象图生成，`onCreate` 没有任何业务初始化。依赖仍按实际使用懒加载：

- **Python** 由 `PythonRuntime.ensureStarted` 在真正调用时启动（`CharacterRepository`、`ModRepository`、`PrepackService`、`MainViewModel` 的各调用点）。
- **角色表 / mod 列表 / 缓存用量** 由各 ViewModel 在界面出现后拉取。

其中角色表刷新（`MainViewModel.startAsyncInitialization` → `CharacterRepository.updateCharacterData` → `PythonRuntime.ensureStarted`）在主界面启动后于**后台协程**异步进行，不阻塞首屏——这是角色表功能的实际使用，不是「抢先」。`HiltEntryPointTest#applicationDoesNotEagerlyStartPython` 断言的是 Application/Hilt 初始化阶段（进程内还没拉过任何 Activity 时）Python 未启动；用 `@FixMethodOrder(NAME_ASCENDING)` 保证它在任何 `mainActivity*` 用例之前跑（JUnit 默认反射顺序不可靠，实测过：不固定顺序时 `mainActivityColdStartsUnderHilt` 先跑并异步拉起 Python，导致该断言假失败——已修）。

## 3. KSP 生成（无 kapt）

`:app:assembleDebug` 后 `app/build/generated/ksp/debug/java/` 生成 Hilt 代码，`app/build` 下**无任何 kapt 目录**（`find … -path "*kapt*"` 为空）：

- `Bd2Application_GeneratedInjector`、`Hilt_MainActivity`、`Hilt_SpinePreviewActivity`、`Hilt_InstallService`、`Hilt_PrepackService`、`Hilt_ScanService`，及各 `*_GeneratedInjector`、`hilt_aggregated_deps/*`、`DaggerBd2Application_HiltComponents_SingletonC`。
- **没有** `Hilt_ShizukuFileService`（确认它未接 Hilt）。
- 依赖图（`releaseRuntimeClasspath`）：`com.google.dagger:dagger:2.58`、`hilt-android:2.58`（androidx.hilt 传递的 2.54 被抬到本组合钉的 2.58）、`hilt-core:2.58`、`androidx.hilt:hilt-lifecycle-viewmodel-compose:1.3.0`、`javax.inject:1`——与 T13 矩阵一致，无意外版本。

## 5. HiltEntryPointTest（4 条）

用真实 `@HiltAndroidApp` 的 `Bd2Application`（不是 `HiltTestApplication`），标准 `AndroidJUnitRunner`，`@FixMethodOrder(NAME_ASCENDING)`。

| 用例 | 断言 |
|---|---|
| `applicationDoesNotEagerlyStartPython` | Application/Hilt 初始化阶段 `Python.isStarted()` 为 false（首个跑，进程内未拉过 Activity） |
| `applicationIsHiltGeneratedProductionApp` | `applicationContext is Bd2Application`；类名含 `Bd2Application`；`DaggerBd2Application_HiltComponents_SingletonC` 可 `Class.forName` |
| `mainActivityColdStartsUnderHilt` | `ActivityScenario` 冷启动到 RESUMED，运行类是 `Hilt_MainActivity` 的子类，`instanceof MainActivity` 成立 |
| `spinePreviewActivityIsHiltEntryPoint` | `Hilt_SpinePreviewActivity` 是 `SpinePreviewActivity` 的可赋值基类（不实拉 WebView） |

**设备：** AVD `bd2-x64-api34`（emulator-5554，API 34），`Test-Bd2Device` 同款判定（`Invoke-Bd2Instrumentation` + `Assert-Bd2InstrumentationResult`，逐条 STATUS_CODE，skip 算失败）。结果 **OK (4 tests)，PASS 4，skip 0**（`local/t16/run3.log`、`local/t16/device/instrumentation.txt`）。AVD 不在白名单，用 `local/t16/run-hilt.ps1` 显式指定 serial。

**为什么不用测试内自定义 `@EntryPoint`（如实登记）：** 第一版在测试里定义了 `SingletonEntryPoint` 想用 `EntryPointAccessors.fromApplication` 取它——设备上 `ClassCastException: Cannot cast …SingletonCImpl to …HiltEntryPointTest$SingletonEntryPoint`。原因：**测试 APK 里声明的 `@EntryPoint` 不会被聚合进应用编译时已生成的 `SingletonComponent`**，要用它得引入 `hilt-android-testing` + `HiltTestApplication`/`@HiltAndroidTest`，那会换成测试专用容器，与「验证生产形态」矛盾。改为直接验证生产形态（Application 是 Hilt 生成类 + 两个 `@AndroidEntryPoint` Activity 真实冷启动）。

**冷启动 UI 复核（minified release）：** `am start -W com.bd2toolsbox/.MainActivity` `Status: ok`、TotalTime 1161 ms，进程存活，角色表加载出来（Alec/艾瑞克…），logcat 无 `FATAL EXCEPTION`/`Hilt`/`EntryPoint not` 错误（`local/t16/coldstart-logcat.txt`）。

minified release x86_64（Hilt 接管的 `Bd2Application`）+ release-probe 在 AVD API 34 上：`ReleasePythonRuntimeProbeTest#productionRuntimeImportsAndBc1` **OK (1 test)**，PID 6696，`PYTHON_RUNTIME_READY payloadAbi=x86_64 python=3.8`（`local/t16/release-runtime-probe.txt`）。这证明 R8 混淆后的 Hilt Application 能正常启动并驱动 Python 入口。

## 7. arm64

按 [arm64-verification-policy.md](../arm64-verification-policy.md)，T16 **不改 native / Python / 打包**（只加 Hilt 注解与生成的 Java 字节码，两个 ABI 执行同一份 dex），属 **B 类**：x86_64 设备验收 + arm64 静态审计。

- x86_64：`HiltEntryPointTest` 4/4、minified release 冷启动 + release-probe PASS（§5、§6）。
- arm64：`app-arm64-v8a-release.apk` 静态审计 **PASS**（failures 0，20 个 decoder 导出齐全，e_machine 183，16 KB 对齐延续 T15；warnings 2 项为既有 `libastcenc` 4 KB 与双 ABI bootstrap），`local/t16/abi-audit-arm64-v8a.json`。
- **未在原生 arm64 运行**（B 类不要求）。Hilt 对象图是 dex 层行为，两个 ABI 相同；x86_64 已实跑。
