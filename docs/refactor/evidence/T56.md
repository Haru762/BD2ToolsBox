## 3. 端到端发现并修掉的缺陷

**`DirectMoveCommitHost` 违反 `MoveCommitHost.execute` 自己文档的契约。**

`MoveCommitHost` 的接口文档写着「要么 `submission` 非空，要么 `failure` 非空」。
但 `InstallExecutor.move` 对**提交前**的校验失败（源文件已改变、目标路径无效、
没有可提交目标、暂存内容与冻结目标不一致）是**抛 `IOException`** 的：

```
java.io.IOException: 源文件已改变，拒绝提交：bundleA/hash1/__data
```

`InstallService.executeRun` 一直有 `catch (e: Exception)` 把它转成
`MoveCommitResult(..., failure = e.message)`，所以生产服务路径没问题；
`DirectMoveCommitHost` 没有 —— 异常直接穿过接口边界，调用方拿到的是抛出而不是
一个「失败了」的结果。已按服务的做法补齐（`CancellationException` 仍原样上抛，
不把取消变成一条「装入失败」的用户提示）。

这条是**只有端到端才能发现**的：`MoveInstallWiringTest`（JVM）注入的是自己的
`DirectMoveCommitHost` 替身，永远不会走到这条路径。

**修的时候又踩了一次**：第一版补丁顺手加了 `import android.util.Log` + `Log.e(...)`，
被架构规则 **R4**（feature 层不得依赖 `android.util.Log`）拦下 —— 上一轮全量检查是在
这个提交之前跑的，所以当时没暴露。现在这里**不写日志**：失败原因已经进
`MoveCommitResult.failure`，生产路径上的 `InstallService` 也会自己记一笔，不会丢。

## 4. 用例与实测

隔离世界：`cacheDir/t56/run<N>/{shared,game,staging}`；「游戏目录」由
`IsolatedGameFileAccess` 指向临时目录，文件操作走**生产** `ShizukuFileService`
（真实 I/O，不经 Shizuku 授权）。故障注入点是 `installConvertedBundle` 返回失败
与「冻结后改源内容」，都不在自己的 fake 上。

| 用例 | 断言 |
|---|---|
| `installWritesTargetAndLedgerWithoutHalfData` | 目标内容 == 产物；账本 1 条；journal 已闭合（`classify()` 为空）；无 `.part` |
| `twoModsOnTheSameBundleAreBothAccounted` | 两个 bundle 各一条账本、各自内容正确；无 `.part` |
| `faultDuringCopyLeavesTargetAndLedgerUntouched` | 复制失败 → 不报成功；失败目标**保持旧内容**；不记账；无 `.part` |
| `contentChangedAfterFreezeIsRejectedBeforeReplace` | 冻结后改源 → 抛 `IOException`；目标**根本没被创建**；账本为空；无 `.part` |
| `uninstallRemovesOnlyTheLedgerRecordAndKeepsSource` | 只移除账本记录；游戏目录内容不被卸载动作改动；源目录状态不变 |
| `successfulInstallLeavesNothingForRecoveryToWorryAbout` | 装完 `OperationRecovery.classify()` 为空（不留「像中断」的痕迹） |
| `unwritableLedgerMakesTheInstallRefuseToTouchTheGameFile` | 账本**从一开始**不可写 → 系统**根本不碰游戏文件**（意图记录写不下去就不往下走） |
| `ledgerWriteFailureAfterTheReplaceLeavesTheWindowRecoveryMustReconcile` | 账本在**替换之后**才不可写 → 文件已换、账本无记录、`classify()` 判待核对 —— **T25 的窗口，由真实失败注入产生** |
| `cancellingBeforeCommitLeavesTheTargetUntouchedAndAllowsRetry` | 排队中取消：终态 `CANCELLED`、参数已释放（`execute` 返回 null 且执行体不被调用）、目标未动、账本空、**可用新任务重试同一目标** |
| `cancellationRequestedInsideTheCommitWindowCannotEraseTheCommittedFact` | 提交临界区里请求取消：`committedTargets` 仍记录「事实落地了」——阶段与事实必须分开读 |

### 两个账本写失败注入为什么分开写

第一版只写了一条「把账本路径变成目录」的用例，断言「文件已换、账本无记录」——
**实测失败**：文件根本没被替换。查提交顺序（`MoveInstallSubmitter.submit`）才明白：

```
beginSubmit → markStaged → markTargetReplacing → moveFiles() → markTargetReplaced → commitLedger
```

前四条都是**写前意图记录**，任何一条失败就「不碰游戏文件」。所以「账本一开始就不可写」
拦在替换之前 —— 这是**更好**的行为，值得单独固定成用例。

要精确命中 T25 的窗口，注入点必须放在**替换之后**：给隔离的 `GameFileAccess` 加
`onBeforeCopy` 钩子，在真实复制前把账本路径变成目录。这样前四条已落盘、文件已换掉，
失败只发生在最后的 `commitLedger`。两条用例各自固定一个语义，缺一不可。

### 隔离保证

账本与 journal 是应用私有真实文件，所以 `@Before` 整份备份、`@After` 原样还原
（不存在就删除）。**不碰真实游戏目录、MOD 源目录、备份根。**

## 2026-10-13 补：真实网络中断的失败注入（下载原子性）

计划要求「在复制/校验/备份/账本/Binder/**网络**各边界注入失败」。网络这一层此前只有
「仓储抛异常」这一种写法，本轮换成**真的会断的 HTTP 响应**。

### 修掉的缺陷：`GamekeeApi.download` 会留下半个文件

原实现直接往最终路径写：

```kotlin
dest.outputStream().use { out -> input.copyTo(out) }
```

连接中途断掉时 `copyTo` 抛异常、被 catch 吞成 `false`，但**半个文件已经落在 `dest` 上**。
而缓存读取只判 `exists() && length() > 0`（`loadThumb`、正文缓存、emoji 缓存都是），
于是那个截断的文件会被当成**有效缓存，而且永远不会重试**；顺带还会把上一次的
有效缓存毁掉。

改成 `AtomicFileWriter().write(target = dest) { ... }`：临时件 + 成功后原子替换 +
失败时删临时件且**旧文件原样保留**。两件事一起解决。

### 测试：`GamekeeDownloadAtomicityTest`（设备，4 条）

本地起 `ServerSocket`，声明很大的 `Content-Length`、只发一小段就关连接 ——
这就是真实断网时的形状，不是 mock。

| 用例 | 断言 |
|---|---|
| `aTruncatedDownloadLeavesNoFileBehind` | 返回 false；目标**不存在**；目录里**没有临时件残留** |
| `aFailedDownloadDoesNotDestroyAnExistingGoodCache` | 已有的有效缓存字节**完全不变** |
| `anUnreachableHostFailsWithoutCreatingAnything` | 连不上时返回 false 且不创建任何文件 |
| `aSuccessfulDownloadStillLandsAtomically` | 正常路径照常落盘、内容逐字节完整、无临时件残留 |

**实测 MuMu x86_64/API32：4/4 PASS。**

### 测试基础设施：debug-only 的本机明文豁免

第一版这三条失败用例**全部「通过」**，而成功用例失败 —— 查出来是 API 28+ **默认禁止明文**，
所以那些用例是因为**根本没连上**而通过的。那是假通过，比测试失败更危险。

新增 `app/src/debug/AndroidManifest.xml` + `src/debug/res/xml/network_security_config.xml`，
**只给 `127.0.0.1` / `localhost` 开明文，且只在 debug 变体**（release 不含）。

并给测试加了「服务器必须真的被连上过」的断言（`accepted` 标志）——
没有它，上面那个假通过会一直存在而没人发现。

## 2026-10-13 补：性能门禁的假数据

16 KB 模拟器上的暖启动样本一度全是 **0 ms**，而门禁**通过了**。

`TotalTime: 0` 不是「很快」，而是「**根本没启动**」（activity 已在前台，
`am start -W` 直接返回）。成因是 `input keyevent HOME` 是异步的，回桌面还没生效就
`am start`。已改成：只接受 `TotalTime > 0` 的样本，取不到就重试（最多 4 次），
4 次都拿不到就报错；冷启动样本同样加了「不得出现 0」的检查。

## 2026-10-13 补：明文豁免与既有用例的冲突（以及怎么解的）

为了让下载原子性用例能真的打到本地服务器，加了 debug-only 的
`network_security_config`（只给 `127.0.0.1` / `localhost` 开明文）。加完之后
**`PlatformBehaviorTest` 从 13/13 变成 1 条失败**：`downloadCompleteBroadcastIsDelivered`
等不到 `ACTION_DOWNLOAD_COMPLETE`。

查证过程（两次决定性实验）：

| 配置 | `PlatformBehaviorTest` |
|---|---|
| 无 debug manifest | **13/13 PASS** |
| 有 manifest，但 config 里**不豁免**明文 | **13/13 PASS** |
| 有 manifest，且豁免 `127.0.0.1` | 1 条失败 |

所以问题**不是** manifest 本身，而是「允许连 `127.0.0.1`」这个策略：
那条用例用的是 `http://127.0.0.1:9/`（没人监听的端口），它依赖「DM 被策略瞬间拦掉
→ 立刻发完成广播」。明文一放开，DM 会**真的去连**，60 秒内等不到完成广播。

**修法**：不改豁免（它是网络失败注入的前提），改那条用例 —— 在测试里起一个
**必定回 404** 的本地服务器，让 DM 拿到一个**真实的 HTTP 错误响应**。
完成广播因此**确定地**发出来，不再依赖「连接被拒」这种不确定的行为。
这比原来更稳：原来那个前提本来就不该被依赖。

改完实测：API 29 上 `PlatformBehaviorTest` **13/13** 且
`GamekeeDownloadAtomicityTest` **4/4** 同时通过；MuMu 上最终设备门禁 **18/18**。
